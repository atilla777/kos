# Интеграция KOS с OpenCode

После установки сервера и CLI пользователь может установить из репозитория KOS глобальные skills, профили и команды OpenCode. Они доступны при работе в разных Git-репозиториях. `/kos-init` помогает первоначальной установке и проверке, `/kos-update` — безопасному обновлению из GitHub, `/kos` — необязательное сокращение для оркестратора в Build. Установка не изменяет существующие настройки моделей. При обновлении распознанные неизменённые копии прежних файлов KOS заменяются; файл с пользовательскими правками или неизвестного происхождения вызывает остановку до копирования. После установки или обновления необходимо открыть новую сессию OpenCode. Проверка наличия команд, профилей, моделей и skill проектной документации описана в [README](../../../README.md).

## Работа с Git и GitHub

Для явной просьбы о работе с Git агент использует skill `kos-git`, для операции GitHub через `gh` — `kos-github-cli`. Они доступны глобально после установки и новой сессии OpenCode; обычная просьба изменить код сама по себе их не вызывает. Для задачи разработки KOS отдельную работу с worktree направляет оркестратор согласно правилам проекта. Перед действием агент проверяет правила текущего проекта, состояние репозитория, необходимые изменения и историю; после — проверяет результат. Для незнакомой операции он читает установленную справку `git` или `gh`, а не ограничивается примерами skill и не придумывает флаги.

Коммит, push, создание или слияние PR выполняются по поручению пользователя или применимому правилу проекта. Способ публикации определяется проектом: skill не навязывает PR вместо локального слияния или наоборот. При конфликте, неверной ветке, неуспешном push/PR либо отсутствующем `gh` агент сообщает текущий результат и сохраняет чужие изменения; при неопределённом исходе сначала проверяет состояние. Сервер KOS не управляет Git или GitHub.

## Обновление установленного KOS

Пользователь вызывает `/kos-update` или просит агента действовать по [инструкциям обновления](../../../README.md#updating-an-existing-installation). Агент сначала проверяет, какой checkout, установленная команда `kos`, постоянная БД и запущенный сервер используются. Для чистой ветки `main`, не имеющей локальных коммитов сверх `origin/main`, он получает актуальные исходники с GitHub без переписывания истории, устанавливает CLI из этих исходников и обновляет распознанные KOS-файлы OpenCode. Проверка сравнивает файлы установленного CLI с исходниками: одинаковый номер версии CLI ещё не доказывает одинаковое содержимое. Новые команды и инструкции видны только после перезапуска OpenCode пользователем.

Если checkout изменён, открыта другая ветка, есть локальные коммиты, GitHub недоступен или установленный файл OpenCode отредактирован, агент сообщает причину и останавливает обновление до решения пользователя. При сбое после обновления части компонентов он сообщает, какие из них обновились, и как продолжить после устранения ошибки; не объявляет всю установку обновлённой. Старый сервер может продолжать работать на прежней версии после обновления файлов.

Проверка постоянной БД показывает ожидающие миграции и их последствия. Перед миграцией агент готовит и проверяет отдельную резервную копию, а затем запрашивает **явное разрешение на миграцию**. **Остановка и перезапуск работающего сервера требуют другого явного разрешения**, с описанием способа запуска. Отказ от любого разрешения оставляет соответствующее действие невыполненным. Ошибка миграции не приводит к автоматическому восстановлению из копии или запуску сервера с непроверенной схемой. Ни `/kos-init`, ни `/kos-update` сами по себе не являются согласием на миграцию, восстановление БД или перезапуск Rails-сервера.

## Повседневный запуск и проверка

При запуске с уже существующей локальной базой задачи и артефакты остаются в постоянном хранилище. Пользователь сначала проверяет, какая база находится в checkout, и сохраняет её перед миграциями; обычный запуск актуального сервера не требует повторной инициализации. Сервер отвечает через loopback, а установленная пользовательская команда `kos` доступна агентам из их `PATH`. Если сервер недоступен, команды сообщают об ошибке соединения; если текущий Git-проект не зарегистрирован, просмотр проекта и доступной работы не создаёт запись автоматически. Пустой список проектов при работающем API означает отсутствие зарегистрированных проектов, а не ошибку запуска.

В Linux сервер можно запускать вручную либо как пользовательский сервис при входе в систему. После его остановки данные остаются на локальном диске и читаются при следующем запуске. Установка или обновление skills требует новой сессии OpenCode: наличие профилей в системном списке не означает, что старая сессия перечитала инструкции. Перед захватом работы пользователь проверяет наличие нужных моделей; уникальный ID рабочей беседы агент получает сам. Если Ruby/Bundler, пользовательский PATH, сервер или модели недоступны, сначала устраняют соответствующую причину; подробные команды и безопасный порядок работы с БД находятся в [README](../../../README.md).

## Выполнение задачи

Пользователь просит основного агента обычными словами обсудить Brief, создать или продолжить задачу KOS; называть skill, переменную `KOS_SESSION_ID` или команду `/kos` не нужно. При реальном запросе о работе в KOS агент сам выбирает `kos-orchestrator`; простое упоминание KOS не является поручением на захват. В read-only Plan можно читать задачи и обсудить с человеком высокоуровневые решения и план Brief без создания задач, захвата или записи артефактов. После согласования агент переходит в Build для сохраняющих действий; если переключение не доступно, просит пользователя переключить режим с сохранением согласованного контекста. Отдельного основного режима KOS нет; установленный ранее профиль `agent/kos-orchestrator.md` нужно удалить, чтобы он исчез из выбора режимов после перезапуска OpenCode.

Для новой рабочей беседы агент один раз получает случайный ID командой `kos session new` и сохраняет его в контексте этой беседы. Она работает без Git-проекта и сервера, выдаёт JSON и ничего не сохраняет в общем файле. В продолжении **той же беседы** агент использует прежний ID: `current --fingerprint` показывает действующий захват и шаг без нового захвата или продления lease. Он сверяет проект, задачу и шаг перед продолжением. Разные независимые агенты не используют общий ID. Оркестратор видит короткий маршрут текущего шага: позицию, исполнителя и, для субагента, уровень модели. В режиме `--fingerprint` CLI возвращает SHA-256-отпечаток вместо полного токена захвата; содержимое инструкций и документов в маршрут не включено.

Шаг `main` оркестратор выполняет сам. Для шага `subagent` уровня `standard` он привлекает профиль GPT-6 Luna, уровня `advanced` — GPT-6 Sol. Уровень выбирается автором workflow по сложности шага; простая разработка тоже может быть `standard`. Исполнитель получает ID задачи, проект, позицию шага, ID сессии и отпечаток захвата, а инструкцию, входные документы и ожидаемые результаты запрашивает самостоятельно через CLI. Полный токен не передаётся в сообщении субагенту. Если вход отсутствует, исполнитель видит это явно и сообщает, если без него невозможно продолжить. Найденные документы содержат источник и версию.

Исполнитель сохраняет результат под действующим захватом всей задачи. При использовании отпечатка CLI дополнительно проверяет ID задачи и текущую позицию шага, получает токен в памяти и передаёт его существующему API. При смене захвата до отправки возникает конфликт без записи; смена между чтением и записью отклоняется сервером. Для создания отсутствующего документа и обновления существующей версии используются разные ожидания; конфликт версии не переписывает более свежий результат. Оркестратор проверяет работу и явно продвигает шаг с ожидаемой позицией либо завершает задачу на последнем шаге. Если шаг поручает субагенту публикацию, тот действует по правилам целевого проекта, а главный агент проверяет подтверждённый результат до завершения задачи в KOS.

## Worktree задачи разработки

Если постановка задачи или правила целевого проекта явно предусматривают разработку, оркестратор перед началом изменения файлов готовит отдельную ветку и worktree задачи. Имена, расположение и базу выбирает по правилам **целевого** проекта. Без соглашения об именах используются короткое имя репозитория и ID задачи: для проекта `shop` задача 42 получает ветку `shop/task-42` и соседний каталог `shop-task-42`; при работе над другим проектом префикс меняется. Заголовок задачи в KOS остаётся прежним. Оркестратор и приглашённые исполнители работают в одном каталоге; Git `origin` по-прежнему определяет тот же KOS-проект, а полный токен захвата субагенту не передаётся. Для задачи без разработки отдельный worktree не требуется.

При продолжении агент проверяет существующие ветку, каталог и принадлежность проекту и использует прежний worktree, сохраняя изменения. Если ветка уже есть без подходящего worktree или путь занят чужой работой, он останавливается и сообщает, что нужно проверить; не создаёт вторую ветку поверх первой. Публикация следует правилам целевого проекта: он определяет назначение, проверки и способ интеграции. Только после подтверждения результата в назначении и при чистом worktree агент безопасно удаляет его. Если публикация не удалась, её результат неясен, каталог содержит изменения или удаление не удалось, каталог остаётся для продолжения и агент сообщает его путь и ветку. `release`, истечение lease и статус `done` сами по себе не удаляют worktree. KOS не проверяет факт публикации.

## Документация целевого проекта

Автор workflow может явно указать в инструкции шага документации загрузить `kos-project-docs`. Главный агент также вызывает его на шаге нормативной спецификации Brief v2. Для документации **реализованного поведения** действуют правила и путь целевого проекта; если они не требуют документацию, этот шаг фиксирует причину отсутствия обновления. Для нормативной спецификации Brief проектные правила определяют формат и путь, а без указанного пути используется `docs/`. Повторный запуск сверяется с существующим текстом, не создавая дубликаты. Спецификация содержит требуемое поведение независимо от готовности реализации; результаты задач KOS отражают прогресс, а документация текущего поведения описывает то, что действительно работает.

Если правила требуют OKF v0.2, новые документы содержат подходящий frontmatter и следуют конвенциям проекта; подтверждение человеком не появляется без настоящей проверки. Если OKF не предписан, сохраняется принятый в проекте формат. Если обязательный путь для документации реализованного поведения не задан или неоднозначен, агент просит уточнить его. Для Brief v2 нормативный документ обязателен и публикуется до завершения задачи; при запрете публикации или конфликтующих правилах агент просит решения человека. Изменения и применимые проверки просматриваются до публикации по правилам проекта. Skill не заменяет проектные документы артефактами KOS и не позволяет серверу оценивать их полноту.

## Продолжение и ошибки

В совершенно новой беседе агент определяет нужную задачу в проекте; если подходит несколько, уточняет выбор. Просмотр задачи показывает предыдущий ID сессии и срок lease, но не полный claim. Пока прежний захват действует, использовать его ID для `current --fingerprint` и продолжения можно **только после явного подтверждения человека, что прежний агент остановлен**, и проверки проекта, ID задачи, шага, срока и прежнего worktree. Без подтверждения ждут истечения lease либо освобождают задачу из доступной прежней беседы. KOS не способен подтвердить остановку процесса самостоятельно.

При долгой работе оркестратор явно продлевает lease. После истечения старая беседа теряет право записи; новая получает собственный ID, повторно захватывает доступную задачу и новый claim. Шаг и сохранённые результаты остаются на месте, существующий worktree проверяется и переиспользуется. Если задача уже завершена или захвачена другим агентом, старый отпечаток не применяется. Неверный ID не находит прежний `current`; смена владельца и повторное продвижение со старой позицией дают конфликт вместо записи. При неопределённом исходе сетевого запроса исполнитель или оркестратор сначала проверяет состояние задачи либо документа, затем решает, нужен ли новый запрос. Никакой клиентский skill не гарантирует, что прерванный агент перестал менять внешние файлы.

Отпечаток не является способом авторизации: локальный KOS не защищает от недоверенных процессов того же пользователя. Обычные команды без `--fingerprint` по-прежнему выводят полный токен владельцу; в инструментах агента их не следует запускать напрямую, поскольку история инструментов сохраняется локально. Настройка моделей относится только к OpenCode. KOS не проверяет использованную модель, содержание выхода, прохождение тестов или факт публикации. Для API шаги `standard` и `advanced` остаются независимыми от конкретного агентного harness.
