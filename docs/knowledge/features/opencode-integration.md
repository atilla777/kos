# Интеграция KOS с OpenCode

После установки сервера и CLI пользователь может установить из репозитория KOS глобальные skills, профили и команды OpenCode. Они доступны при работе в разных Git-репозиториях. `/kos-init` помогает первоначальной установке и проверке, `/kos-update` — безопасному обновлению из GitHub, `/kos` — запуску существующего оркестратора в Build. Установка не изменяет существующие настройки моделей. При обновлении распознанные неизменённые копии прежних файлов KOS заменяются; файл с пользовательскими правками или неизвестного происхождения вызывает остановку до копирования. После установки или обновления необходимо открыть новую сессию OpenCode. Проверка наличия команд, профилей и моделей описана в [README](../../../README.md).

## Работа с Git и GitHub

Для явной просьбы о работе с Git агент использует skill `kos-git`, для операции GitHub через `gh` — `kos-github-cli`. Они доступны глобально после установки и новой сессии OpenCode; обычная просьба изменить код сама по себе их не вызывает. Перед действием агент проверяет правила текущего проекта, состояние репозитория, необходимые изменения и историю; после — проверяет результат. Для незнакомой операции он читает установленную справку `git` или `gh`, а не ограничивается примерами skill и не придумывает флаги.

Коммит, push, создание или слияние PR выполняются по поручению пользователя или применимому правилу проекта. Способ публикации определяется проектом: skill не навязывает PR вместо локального слияния или наоборот. При конфликте, неверной ветке, неуспешном push/PR либо отсутствующем `gh` агент сообщает текущий результат и сохраняет чужие изменения; при неопределённом исходе сначала проверяет состояние. Skills не создают и не удаляют worktree задачи и не дают серверу KOS полномочий управлять Git или GitHub.

## Обновление установленного KOS

Пользователь вызывает `/kos-update` или просит агента действовать по [инструкциям обновления](../../../README.md#updating-an-existing-installation). Агент сначала проверяет, какой checkout, установленная команда `kos`, постоянная БД и запущенный сервер используются. Для чистой ветки `main`, не имеющей локальных коммитов сверх `origin/main`, он получает актуальные исходники с GitHub без переписывания истории, устанавливает CLI из этих исходников и обновляет распознанные KOS-файлы OpenCode. Проверка сравнивает файлы установленного CLI с исходниками: одинаковый номер версии CLI ещё не доказывает одинаковое содержимое. Новые команды и инструкции видны только после перезапуска OpenCode пользователем.

Если checkout изменён, открыта другая ветка, есть локальные коммиты, GitHub недоступен или установленный файл OpenCode отредактирован, агент сообщает причину и останавливает обновление до решения пользователя. При сбое после обновления части компонентов он сообщает, какие из них обновились, и как продолжить после устранения ошибки; не объявляет всю установку обновлённой. Старый сервер может продолжать работать на прежней версии после обновления файлов.

Проверка постоянной БД показывает ожидающие миграции и их последствия. Перед миграцией агент готовит и проверяет отдельную резервную копию, а затем запрашивает **явное разрешение на миграцию**. **Остановка и перезапуск работающего сервера требуют другого явного разрешения**, с описанием способа запуска. Отказ от любого разрешения оставляет соответствующее действие невыполненным. Ошибка миграции не приводит к автоматическому восстановлению из копии или запуску сервера с непроверенной схемой. Ни `/kos-init`, ни `/kos-update` сами по себе не являются согласием на миграцию, восстановление БД или перезапуск Rails-сервера.

## Повседневный запуск и проверка

При запуске с уже существующей локальной базой задачи и артефакты остаются в постоянном хранилище. Пользователь сначала проверяет, какая база находится в checkout, и сохраняет её перед миграциями; обычный запуск актуального сервера не требует повторной инициализации. Сервер отвечает через loopback, а установленная пользовательская команда `kos` доступна агентам из их `PATH`. Если сервер недоступен, команды сообщают об ошибке соединения; если текущий Git-проект не зарегистрирован, просмотр проекта и доступной работы не создаёт запись автоматически. Пустой список проектов при работающем API означает отсутствие зарегистрированных проектов, а не ошибку запуска.

В Linux сервер можно запускать вручную либо как пользовательский сервис при входе в систему. После его остановки данные остаются на локальном диске и читаются при следующем запуске. Установка или обновление skills требует новой сессии OpenCode: наличие профилей в системном списке не означает, что старая сессия перечитала инструкции. Перед захватом работы пользователь проверяет наличие нужных моделей и задаёт уникальный идентификатор сессии. Если Ruby/Bundler, пользовательский PATH, сервер или модели недоступны, сначала устраняют соответствующую причину; подробные команды и безопасный порядок работы с БД находятся в [README](../../../README.md).

## Выполнение задачи

Пользователь в режиме Build просит основного агента загрузить skill `kos-orchestrator` и задаёт уникальную постоянную идентичность сессии. Отдельного основного режима KOS нет; установленный ранее профиль `agent/kos-orchestrator.md` нужно удалить, чтобы он исчез из выбора режимов после перезапуска OpenCode. Оркестратор восстанавливает существующий действующий захват либо захватывает задачу и видит короткий маршрут текущего шага: позицию, исполнителя и, для субагента, уровень модели. В режиме `--fingerprint` CLI возвращает SHA-256-отпечаток вместо полного токена захвата; содержимое инструкций и документов в маршрут не включено.

Шаг `main` оркестратор выполняет сам. Для шага `subagent` уровня `standard` он привлекает профиль GPT-6 Luna, уровня `advanced` — GPT-6 Sol. Уровень выбирается автором workflow по сложности шага; простая разработка тоже может быть `standard`. Исполнитель получает ID задачи, проект, позицию шага, ID сессии и отпечаток захвата, а инструкцию, входные документы и ожидаемые результаты запрашивает самостоятельно через CLI. Полный токен не передаётся в сообщении субагенту. Если вход отсутствует, исполнитель видит это явно и сообщает, если без него невозможно продолжить. Найденные документы содержат источник и версию.

Исполнитель сохраняет результат под действующим захватом всей задачи. При использовании отпечатка CLI дополнительно проверяет ID задачи и текущую позицию шага, получает токен в памяти и передаёт его существующему API. При смене захвата до отправки возникает конфликт без записи; смена между чтением и записью отклоняется сервером. Для создания отсутствующего документа и обновления существующей версии используются разные ожидания; конфликт версии не переписывает более свежий результат. Оркестратор проверяет работу и явно продвигает шаг с ожидаемой позицией либо завершает задачу на последнем шаге. Если правила проекта требуют публикации, её выполняет главный агент согласно этим правилам.

## Продолжение и ошибки

При долгой работе оркестратор явно продлевает lease. После его истечения старый отпечаток больше не даёт права записи: агент проверяет текущую задачу и повторно захватывает её, если она доступна. Шаг и сохранённые результаты остаются на месте. Повторное продвижение с прежней позицией получает конфликт. При неопределённом исходе сетевого запроса исполнитель или оркестратор сначала проверяет состояние задачи либо документа, затем решает, нужен ли новый запрос. Никакой клиентский skill не гарантирует, что прерванный агент перестал менять внешние файлы.

Отпечаток не является способом авторизации: локальный KOS не защищает от недоверенных процессов того же пользователя. Обычные команды без `--fingerprint` по-прежнему выводят полный токен владельцу; в инструментах агента их не следует запускать напрямую, поскольку история инструментов сохраняется локально. Настройка моделей относится только к OpenCode. KOS не проверяет использованную модель, содержание выхода, прохождение тестов или факт публикации. Для API шаги `standard` и `advanced` остаются независимыми от конкретного агентного harness.
