# Интеграция KOS с OpenCode

После установки сервера и CLI пользователь может установить из репозитория KOS глобальные skills, профили и команды OpenCode. Они доступны при работе в разных Git-репозиториях. `/kos-init` помогает первоначальной установке и проверке, `/kos-update` — безопасному обновлению из GitHub, `/kos` — общее необязательное сокращение для оркестратора в Build, `/kos-brief` — для Brief, `/kos-fix` — для Fix. Команды Brief и Fix принимают пояснение после имени и передают его тому же оркестратору; они не меняют требования о согласовании Brief и не требуют предварительного Brief для Fix. Установка не изменяет существующие настройки моделей. При обновлении распознанные неизменённые копии прежних файлов KOS заменяются; файл с пользовательскими правками или неизвестного происхождения вызывает остановку до копирования. Сверка установленных файлов с выбранным checkout доступна без изменения установки: она показывает отсутствующие и отличающиеся KOS-файлы. При обнаруженном расхождении агент выясняет его причину и использует безопасное обновление, не объявляя старую сессию единственной причиной. Совпадение файлов не доказывает, что уже открытая сессия использует их текст; после установки или обновления необходимо открыть новую сессию OpenCode и проверить доступность обновлённого навыка. Агент, получивший только ссылку на KOS, начинает с [маршрута в README](../../../README.md#for-an-agent-install-kos-from-this-repository): проверяет существующую установку и постоянную БД, затем сервер, CLI, общие workflow и OpenCode. Проверка наличия команд, профилей, моделей и skill проектной документации описана там же.

Глобальная установка не выбирает рабочий проект и не изменяет чужие репозитории. Для **явно выбранного** проекта установочный skill после проверки Git `origin` бережно создаёт либо дополняет его `AGENTS.md` краткой инструкцией о работе через KOS и обязательной OKF v0.2 спецификации требований внутри `docs/` (либо выбранного проектом подкаталога); повторение не дублирует её, конфликтующее правило требует уточнения. Язык человека используется при общении, если `AGENTS.md` проекта не закрепляет другой. Инструкция не содержит секретов, claim или локальных путей конкретного компьютера.

При подключении выбранного проекта обязательно создают или сохраняют `rules/index.md` — вход в набор OKF v0.2 правил разработки. Новый `AGENTS.md` создают по шаблону KOS со ссылкой на этот индекс и выбранный индекс спецификаций; существующий файл бережно дополняют по тому же образцу, не затирая прежние правила. Индекс ссылается на действующие правила, оставшиеся в `AGENTS.md`; перенести их текст можно только после отдельного согласования. Отсутствие ещё не согласованных правил архитектуры или стиля не заполняют шаблонными предписаниями. Повторное подключение не дублирует содержание, а при противоречии агент просит решение человека до правки. Обновление глобальной установки само по себе не переписывает выбранный или произвольный проект.

Инструкция подключения проекта полностью доступна через отдельный skill OpenCode. Агент загружает его при подключении выбранного проекта; при обычной работе в уже подготовленном проекте он не запрашивает чтение отдельного файла в глобальном каталоге настроек. Если skill не установлен или OpenCode ещё использует старую сессию, агент сообщает, что нужно завершить установку или открыть новую сессию, вместо обхода запроса разрешения ко всему каталогу настроек.

## Работа с Git и GitHub

Для явной просьбы о работе с Git агент использует skill `kos-git`, для операции GitHub через `gh` — `kos-github-cli`. Они доступны глобально после установки и новой сессии OpenCode; обычная просьба изменить код сама по себе их не вызывает. Для задачи разработки KOS отдельную работу с worktree направляет оркестратор согласно правилам проекта. Перед действием агент проверяет правила текущего проекта, состояние репозитория, необходимые изменения и историю; после — проверяет результат. Для незнакомой операции он читает установленную справку `git` или `gh`, а не ограничивается примерами skill и не придумывает флаги.

Коммит, push, создание или слияние PR выполняются по поручению пользователя или применимому правилу проекта. Способ публикации определяется проектом: skill не навязывает PR вместо локального слияния или наоборот. При конфликте, неверной ветке, неуспешном push/PR либо отсутствующем `gh` агент сообщает текущий результат и сохраняет чужие изменения; при неопределённом исходе сначала проверяет состояние. Сервер KOS не управляет Git или GitHub.

## Обновление установленного KOS

Пользователь вызывает `/kos-update` или просит агента действовать по [инструкциям обновления](../../../README.md#updating-an-existing-installation). Агент сначала проверяет, какой checkout, установленная команда `kos`, постоянная БД и запущенный сервер используются. Для чистой ветки `main`, не имеющей локальных коммитов сверх `origin/main`, он получает актуальные исходники с GitHub без переписывания истории, устанавливает CLI из этих исходников и обновляет распознанные KOS-файлы OpenCode. Проверка сравнивает файлы установленного CLI с исходниками: одинаковый номер версии CLI ещё не доказывает одинаковое содержимое. Новые команды и инструкции видны только после перезапуска OpenCode пользователем.

Если checkout изменён, открыта другая ветка, есть локальные коммиты, GitHub недоступен или установленный файл OpenCode отредактирован, агент сообщает причину и останавливает обновление до решения пользователя. При сбое после обновления части компонентов он сообщает, какие из них обновились, и как продолжить после устранения ошибки; не объявляет всю установку обновлённой. Старый сервер может продолжать работать на прежней версии после обновления файлов.

Проверка постоянной БД показывает ожидающие миграции и их последствия. Перед миграцией агент готовит и проверяет отдельную резервную копию, а затем запрашивает **явное разрешение на миграцию**. **Остановка и перезапуск работающего сервера требуют другого явного разрешения**, с описанием способа запуска. Отказ от любого разрешения оставляет соответствующее действие невыполненным. Ошибка миграции не приводит к автоматическому восстановлению из копии или запуску сервера с непроверенной схемой. Ни `/kos-init`, ни `/kos-update` сами по себе не являются согласием на миграцию, восстановление БД или перезапуск Rails-сервера.

## Повседневный запуск и проверка

При запуске с уже существующей локальной базой задачи и артефакты остаются в постоянном хранилище. Пользователь сначала проверяет, какая база находится в checkout, и сохраняет её перед миграциями; обычный запуск актуального сервера не требует повторной инициализации. Сервер отвечает через loopback, а установленная пользовательская команда `kos` доступна агентам из их `PATH`. При отказе подключения к адресу по умолчанию `http://127.0.0.1:3137` CLI возвращает `connection_error`, указывает этот адрес и подсказывает проверить уже установленный сервер и запустить его командой `mise run kos`; это не означает, что база отсутствует или её нужно инициализировать. Для других адресов, времени ожидания и неверного ответа ошибка остаётся нейтральной, без догадки об остановке сервера. Если текущий Git-проект не зарегистрирован, просмотр проекта и доступной работы не создаёт запись автоматически. Пустой список проектов при работающем API означает отсутствие зарегистрированных проектов, а не ошибку запуска.

В Linux сервер запускается вручную командой `mise run kos` из любого проекта под домашним каталогом после добавления задачи в `~/mise.toml` с рабочим каталогом KOS; без такой настройки команда доступна из checkout KOS. Docker собирает и запускает контейнер в текущем терминале, API доступен только на `127.0.0.1:3137`. CLI по умолчанию использует этот адрес. По Ctrl+C контейнер останавливается и API перестаёт отвечать; после повторного запуска задачи и артефакты остаются в том же каталоге SQLite на диске хоста. Порт 3000 остаётся свободным для других приложений. Старый пользовательский `kos.service` перед работой с этой же БД должен быть остановлен и отключён; два сервера не должны использовать её одновременно. Если Docker, mise или сервер недоступны, агент сначала проверяет соответствующий компонент, а не создаёт новую БД. Установка или обновление skills требует новой сессии OpenCode: наличие профилей в системном списке не означает, что старая сессия перечитала инструкции. Перед захватом работы пользователь проверяет наличие нужных моделей; уникальный ID рабочей беседы агент получает сам. Если Ruby/Bundler, пользовательский PATH, сервер или модели недоступны, сначала устраняют соответствующую причину; подробные команды и безопасный порядок работы с БД находятся в [README](../../../README.md).

## Выполнение задачи

В новых Execution/Fix v7 завершающий шаг совмещает проверку нормативной документации и публикацию одним исполнителем `standard`. Он отдельно записывает результат проверки документов до публикации; если поздняя правка меняет уже проверенное поведение, главный агент обеспечивает затронутые проверки и повторный независимый обзор до продолжения публикации. При публикации в отдельном рабочем каталоге итоговое сообщение различает подтверждённый удалённый результат и локальную основную ветку, если их состояние различается; следующая задача основывается на проверенном удалённом состоянии без перезаписи чужой работы.

После `workflow list --brief` оркестратор читает полное определение лишь выбранной схемы по ID. Если он выводит отдельные поля локальным фильтром JSON, то проверяет, что они действительно присутствуют: у шага есть `name` и `instructions`, а позиция задаётся порядком в массиве с нуля. Вывод из одних `null` при ошибке в имени поля не считается обзором схемы.

Пользователь просит основного агента обычными словами обсудить Brief, создать или продолжить задачу KOS; называть skill, переменную `KOS_SESSION_ID` или команду `/kos` не нужно. При реальном запросе о работе в KOS агент сам выбирает `kos-orchestrator`; простое упоминание KOS не является поручением на захват. В read-only Plan можно читать задачи и обсудить с человеком высокоуровневые решения и план Brief без создания задач, захвата или записи артефактов. После согласования агент переходит в Build для сохраняющих действий; если переключение не доступно, просит пользователя переключить режим с сохранением согласованного контекста. Отдельного основного режима KOS нет; установленный ранее профиль `agent/kos-orchestrator.md` нужно удалить, чтобы он исчез из выбора режимов после перезапуска OpenCode.

В Build пользователь может вызвать `/kos-brief <цель>` для нового или продолжаемого Brief либо `/kos-fix <симптомы>` для исправления по Fix. Новые задачи получают установленную общую версию v7; существующие продолжаются со своей прежней версией. Если сведений для определения задачи недостаточно или подходят несколько задач, агент уточняет их. Команды используют обычные правила выбранного проекта, сессии, захвата и публикации; исправление не создаёт обязательную предварительную задачу Brief. Продолжение уже захваченной задачи проверяется по тем же правилам, что и при `/kos`.

Если пользователь просит начать **новый проект** из пустой папки либо без папки, агент сначала обсуждает местоположение, имя и владельца репозитория, способ подготовки удалённого репозитория, границу доступа и назначение публикации по правилам проекта. Он проверяет учётную запись и доступ на выбранном хосте (GitHub не требуется для других хостов), существующие файлы и настоящий `origin`, не подменяя их предположением по имени папки. Отдельно согласует подготовку репозитория, затем создание и публикацию исходного коммита; проверяет опубликованную основу в согласованном назначении до создания или захвата Brief. Для уже подготовленного проекта он повторно использует проверенные файлы и Git- и KOS-записи без новых репозитория, коммита и задач. Агент бережно добавляет инструкцию KOS в проектный `AGENTS.md`, находит общий Brief v7 и создаёт его задачу с проверенным ID workflow. Если новая версия недоступна, он сообщает о неполном обновлении вместо выбора старой. Задача атомарно регистрирует проект KOS. При конфликте адреса, недоступном назначении или неопределённом результате публикации агент сверяет фактическое состояние и выясняет необходимое действие вместо объявления успеха. Разрешения на подготовку и исходный коммит не являются одобрением требований и плана Brief: их утверждают отдельно.

Для новой рабочей беседы агент один раз получает случайный ID командой `kos session new` и сохраняет его в контексте этой беседы. Она работает без Git-проекта и сервера, выдаёт JSON и ничего не сохраняет в общем файле. В продолжении **той же беседы** агент использует прежний ID: `current --fingerprint` показывает действующий захват и шаг без нового захвата или продления lease. Он сверяет проект, задачу и шаг перед продолжением. Разные независимые агенты не используют общий ID. Оркестратор видит короткий маршрут текущего шага: позицию, исполнителя и, для субагента, уровень модели. В режиме `--fingerprint` CLI возвращает SHA-256-отпечаток вместо полного токена захвата; содержимое инструкций и документов в маршрут не включено.

Шаг `main` оркестратор выполняет сам. Для шага `subagent` уровня `standard` он привлекает профиль GPT-6 Luna, уровня `advanced` — GPT-6 Sol. Уровень выбирается автором workflow по сложности шага; простая разработка тоже может быть `standard`. Исполнитель получает ID задачи, проект, позицию шага, ID сессии и отпечаток захвата, а инструкцию, входные документы и ожидаемые результаты запрашивает самостоятельно через CLI. Полный токен не передаётся в сообщении субагенту. Если вход отсутствует, исполнитель видит это явно и сообщает, если без него невозможно продолжить. Найденные документы содержат источник и версию.

Для выбора схемы и ориентации в задаче оркестратор сначала получает краткий ответ `workflow list --brief`, а для состояния выбранной задачи — `task show ID --state`; связи при необходимости читает через `--brief`. Нужный документ читает отдельно, а полный просмотр вызывает лишь когда нужен весь контекст. Исполнитель получает полный пакет шага, когда нужны тексты входов и шаблоны; для повторной ориентировки на том же шаге ему достаточно `task step show ID --brief`. Успешное продвижение шага уже возвращает следующий маршрут и отпечаток захвата; повторное чтение `current` нужно при возобновлении, длительном перерыве или неопределённом результате. Перед защищённой записью владение всё равно проверяется.

Если достаточно состояния и версий собственных результатов выбранной задачи, оркестратор использует `task show ID --state` и запрашивает следующую порцию при неполной выдаче. За связями и происхождением результатов он обращается к `--brief`, за доказательствами и замечаниями — к нужному результату по ключу. Последний `review_report` читается целиком, когда требуется оценить доказательства; для поиска отдельных замечаний основной агент может вывести нужный фрагмент из ответа CLI локальным фильтром без серверной интерпретации текста.

Если для сверки результата основному агенту нужен только один шаблон, он выводит из полного ответа CLI выбранное поле JSON, не помещая остальные входные документы в свой контекст. Это сокращает видимый вывод, но сервер по-прежнему передаёт полный пакет локальному фильтру; краткий пакет не содержит шаблонов. Глобальные параметры CLI указываются до имени ресурса: `kos --project KEY --session ID task list`. Для выбора шаблона `test_report` пригоден пример `kos --project KEY task step show ID | jq -r '.data.step.templates.test_report'` при наличии `jq`. Исполнитель по-прежнему получает полный пакет, когда для работы нужны все входы.

Если независимая проверка нашла обязательные замечания, оркестратор передаёт исполнителю их краткие идентификаторы, а тот читает последний `review_report` сам, исправляет замечания и выполняет затронутые проверки. Последний `review_report` определяет текущий итог независимой проверки; более ранние отчёты отражают состояние на момент их записи. После исправления и повторной проверки независимый обзор обязателен.

Исполнитель сохраняет результат под действующим захватом всей задачи. При использовании отпечатка CLI дополнительно проверяет ID задачи и текущую позицию шага, получает токен в памяти и передаёт его существующему API. При смене захвата до отправки возникает конфликт без записи; смена между чтением и записью отклоняется сервером. Для создания отсутствующего документа и обновления существующей версии используются разные ожидания; конфликт версии не переписывает более свежий результат. Оркестратор проверяет работу и явно продвигает шаг с ожидаемой позицией либо завершает задачу на последнем шаге. Если шаг поручает субагенту публикацию, тот действует по правилам целевого проекта, а главный агент проверяет подтверждённый результат до завершения задачи в KOS.

При выборе работы агент сначала смотрит список задач и читает состояние только подходящего кандидата; если нужны связи, читает его `--brief`. Сохранённые результаты сверяются с шаблоном полного пакета шага, если он есть: краткий пакет шаблона не содержит. Для вопроса о новом требуемом поведении исполнитель обращается к главному агенту; тот получает явное согласие человека и передаёт ответ исполнителю. Пока ответа нет, технический план может отметить вопрос открытым, но не даёт права менять норму или реализовать зависящее от ответа поведение. После исправлений и поздних правок повторяются затронутые проверки; полный набор — когда этого требуют правила проекта или прежняя проверка более не подтверждает изменение. Независимый обзор и подтверждение публикации остаются обязательными.

## Worktree задачи разработки

При подготовке и публикации агент повторно использует ранее проверенные сведения о репозитории, рабочем каталоге и результатах проверок, пока соответствующее состояние достоверно не изменилось. После правок, долгого перерыва или неясного исхода сверяет его вновь; конечное назначение публикации проверяет независимо от предыдущих проверок. Недоступный hook не подтверждает выполнение его команд: применимые обязательные проверки выполняются отдельно; при невозможности их провести публикация ожидает разрешения препятствия согласно правилам проекта.

Если постановка задачи или правила целевого проекта явно предусматривают разработку, оркестратор перед началом изменения файлов готовит отдельную ветку и worktree задачи. Имена, расположение и базу выбирает по правилам **целевого** проекта. Без соглашения об именах используются короткое имя репозитория и ID задачи: для проекта `shop` задача 42 получает ветку `shop/task-42` и соседний каталог `shop-task-42`; при работе над другим проектом префикс меняется. Заголовок задачи в KOS остаётся прежним. Оркестратор и приглашённые исполнители работают в одном каталоге; Git `origin` по-прежнему определяет тот же KOS-проект, а полный токен захвата субагенту не передаётся. Для задачи без разработки отдельный worktree не требуется.

Полная процедура подготовки, восстановления и удаления worktree загружается через отдельный skill OpenCode, только когда он нужен задаче; чтение самостоятельного файла процедуры в глобальном каталоге настроек не требуется.

При продолжении агент проверяет существующие ветку, каталог и принадлежность проекту и использует прежний worktree, сохраняя изменения. Если ветка уже есть без подходящего worktree или путь занят чужой работой, он останавливается и сообщает, что нужно проверить; не создаёт вторую ветку поверх первой. Публикация следует правилам целевого проекта: он определяет назначение, проверки и способ интеграции. Только после подтверждения результата в назначении и при чистом worktree агент безопасно удаляет его. Если публикация не удалась, её результат неясен, каталог содержит изменения или удаление не удалось, каталог остаётся для продолжения и агент сообщает его путь и ветку. `release`, истечение lease и статус `done` сами по себе не удаляют worktree. KOS не проверяет факт публикации.

## Документация целевого проекта

Действующие правила разработки доступны через `rules/index.md` и применяются при планировании, исполнении, обзоре и публикации. Значимые технические решения по необходимости описывают отдельными ADR в `docs/adr/` с OKF v0.2 frontmatter и навигацией: контекст, альтернативы, выбор и последствия. ADR сохраняет основания, но не заменяет действующее правило. Если корень набора спецификаций — `docs/`, раздел `docs/adr/` входит в него; при корне в выбранном подкаталоге ADR могут быть соседним самостоятельным набором. Шаг документации проверяет также затронутые правила и необходимость ADR; при отсутствии правок в отчёте объясняет почему. Существенно менять правила без согласия человека нельзя.

Общие workflow явно вызывают `kos-project-docs` для нормативной спецификации Brief и при проверке документов в Execution/Fix; планирование отдельной задачи также вызывает его, если требуется согласованное уточнение нормы. Человек или агент может готовить OKF-спецификацию вне KOS. Во всех случаях новое или изменённое требование становится нормой только после явного согласия человека. Спецификации организованы по предметным областям в OKF v0.2 bundle внутри `docs/`; проект может выбрать подкаталог, иначе корень — `docs/`. Повторный запуск сверяется с существующим текстом, не создавая дубликаты. Проектные документы определяют требуемое поведение независимо от готовности реализации, код и проверки — фактическое, задачи KOS — прогресс.

Каждый концепт содержит подходящий OKF v0.2 frontmatter, а корневой индекс обеспечивает навигацию; `verified: human:...` не добавляется без фактического подтверждения. Для Brief нормативный документ обязателен и публикуется до завершения задачи; при запрете публикации или конфликтующих правилах агент просит решения человека. Для Execution/Fix при неизменной норме достаточно проверить затронутые концепты и записать причину отсутствия правок. Изменения и применимые проверки просматриваются до публикации по правилам проекта; после существенных правок повторяется затронутое независимое ревью. Skill не заменяет проектные документы артефактами KOS и не позволяет серверу оценивать их полноту.

## Продолжение и ошибки

В совершенно новой беседе агент определяет нужную задачу в проекте; если подходит несколько, уточняет выбор. Просмотр задачи показывает предыдущий ID сессии и срок lease, но не полный claim. Пока прежний захват действует, использовать его ID для `current --fingerprint` и продолжения можно **только после явного подтверждения человека, что прежний агент остановлен**, и проверки проекта, ID задачи, шага, срока и прежнего worktree. Без подтверждения ждут истечения lease либо освобождают задачу из доступной прежней беседы. KOS не способен подтвердить остановку процесса самостоятельно.

Новый захват и продление дают один час от времени серверной операции. При долгой работе оркестратор задаёт исполнителю контрольную точку до окончания аренды: исполнитель возвращает краткий промежуточный результат, оркестратор сверяет владение и явно продлевает аренду до следующего вызова. Один непрерывный вызов может всё же длиться больше часа; автоматического продления нет. После истечения прежний захват теряет право записи: исполнитель останавливает защищённые операции, оркестратор проверяет состояние задачи, документов и рабочего каталога и повторно захватывает задачу только если она доступна. Шаг и сохранённые результаты остаются на месте; новый захват получает новый отпечаток. При возобновлении в новой беседе действуют отдельные правила подтверждения остановки старого агента. Если задачу уже забрал другой агент или она завершена, старый отпечаток не применяется. Неверный ID не находит прежний `current`; смена владельца и повторное продвижение со старой позицией дают конфликт вместо записи. При неопределённом исходе запроса состояние сначала проверяют. Никакой клиентский skill не гарантирует, что прерванный агент перестал менять внешние файлы.

Отпечаток не является способом авторизации: локальный KOS не защищает от недоверенных процессов того же пользователя. Обычные команды без `--fingerprint` по-прежнему выводят полный токен владельцу; в инструментах агента их не следует запускать напрямую, поскольку история инструментов сохраняется локально. Настройка моделей относится только к OpenCode. KOS не проверяет использованную модель, содержание выхода, прохождение тестов или факт публикации. Для API шаги `standard` и `advanced` остаются независимыми от конкретного агентного harness.

Оркестратор продолжает оставшиеся шаги, исправления и восстановимые проверки без очередного разрешения человека; при неопределённом результате сначала сверяет состояние. Если нужна действительно недоступная ему операция или выбор, он на языке человека кратко объясняет положение дел, смысл решения и точное необходимое действие. В обычном сообщении — один вопрос с ожиданием ответа перед следующим; если среда предоставляет опросник с последовательным показом вопросов, можно задать несколько в одном опроснике. Варианты выбора обозначены цифрами с предложением ответить одной цифрой на каждый вопрос; сквозные ID вопросов Brief остаются отдельными. Агент предлагает обоснованную рекомендацию с короткой причиной в скобках для каждого вопроса; для неизвестных фактов рекомендует способ их выяснить без выдуманного ответа. Все обращения к человеку, в том числе отчёты о ходе работы, препятствиях и завершении, понятны без лишнего жаргона и англицизмов, кроме общеупотребительных слов и точных названий команд или файлов. После подтверждённой публикации и `complete` главный агент сообщает ход работы и проверки, результат для пользователя, место публикации, следующую задачу и дальнейшие действия (например, открыть новую сессию в проекте и вызвать `/kos`). Если доступной задачи нет или публикация не подтверждена, агент не сообщает, что незавершённая задача выполнена.
