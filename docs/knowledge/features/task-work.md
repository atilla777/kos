# Работа с задачами

KOS позволяет работать с задачами одного проекта через CLI `kos` или JSON API. В репозитории с поддерживаемым Git `origin` CLI определяет проект автоматически; вне него пользователь указывает проект явно. Создание проектного workflow, группы либо задачи с общим workflow в новом проекте также создаёт запись проекта, но чтение этого не делает. Задачи создаются после регистрации своего проектного или общего для всех проектов workflow. Для создания новой задачи Brief в OpenCode без репозитория сначала подготавливают настоящий Git-репозиторий: ей предстоит опубликовать спецификацию.

## Планирование и выбор

Новая задача появляется как `planned` на первом шаге указанного workflow. Пользователь может задать её постановку, группу-эпик и задачи, которые требуется закончить до начала работы. Незавершённые блокеры делают задачу недоступной; после их завершения она появляется среди доступных при прочих равных условиях. Группа показывает вычисляемый прогресс и считается завершённой только если в ней есть задачи и все они завершены.

При планировании Brief несколько связанных задач можно создать одним согласованным набором: результатом служат ID и зависимости каждой задачи. Все задачи набора зависят от Brief до его завершения. Неудача проверки любой задачи или связи не оставляет части набора. Для одного Brief сохраняется только один набор; повтор того же запроса узнаёт прежний результат, а другой набор вызывает конфликт. После потери ответа сохранённый результат читается по ключу повтора без действующего захвата, но создание или повтор записи требуют действующего захвата и неизменного шага. Обычное создание отдельной задачи остаётся доступным.

Список доступных задач — снимок: другой исполнитель может захватить задачу до следующего действия пользователя. Запрос «захватить следующую» выбирает и захватывает доступную задачу одним действием и возвращает её контекст. Если подходящих задач нет, результат содержит `task: null` и причину `no_ready_tasks`.

Для просмотра истории и поиска незавершённой работы общий `kos task list` принимает необязательный `--filter done|unfinished|blocked` (API `filter` с теми же значениями). `done` означает статус `done`; `unfinished` включает `planned` и `in_progress` независимо от срока захвата. `blocked` показывает только незавершённые задачи, у которых есть непосредственный блокер со статусом, отличным от `done`. Действующий захват сам по себе не считается блокировкой; незавершённая задача не обязательно доступна для захвата. Без фильтра список остаётся прежним, неверное значение даёт машиночитаемую ошибку. Фильтрацию до выдачи страниц выполняет сервер; после `pagination.next_after_id` вызывающий передаёт тот же фильтр на следующей странице. Изменение зависимостей или статусов между запросами может изменить состав списка; при неизменном состоянии страницы не пропускают подходящие задачи. Для выбора новой работы используют `task ready` или атомарный `claim-next`, а для действующего захвата — `current`.

## Захват и продолжение

Для захвата исполнитель передаёт постоянный для своей сессии идентификатор. CLI может выдать новый случайный ID через `kos session new` даже вне проекта и без сервера; независимые вызовы дают разные ID, поэтому для продолжения работы исполнитель повторно использует прежний. Другие клиенты по-прежнему могут передавать собственный ID. В одном проекте сессия может владеть не более одной активной задачей. Повторный запрос той же задачи той же сессией либо «захватить следующую» возвращает её текущий захват без продления. `current` позволяет восстановить текущую задачу после потери ответа или перезапуска клиента.

Новый захват и явное `renew` устанавливают срок на один час от времени операции на сервере; уже выданный срок при изменении правила не переписывается. Просмотр задачи срок не продлевает. После истечения срока задача остаётся `in_progress`, но снова может быть захвачена. Прежний захват уже не даёт права продлить, изменить или завершить задачу и не может перезаписать результаты нового владельца. Если сессия пытается взять другую задачу при действующем захвате, она получает конфликт.

## Контекст и результаты

Просмотр, `current` и успешный захват по умолчанию показывают постановку и текущий итог работы, группу, собственные артефакты, непосредственных блокеров и их результаты с указанием исходной задачи, а также зависимые задачи и причины недоступности. Большие наборы контекста задачи возвращаются порциями с указанием, как запросить продолжение. Оркестратор может запросить компактный маршрут без документов; инструкцию и входы исполнитель получает в [пакете шага](workflow-steps.md). Обычный просмотр не раскрывает секрет чужого захвата.

Исполнитель сохраняет именованные Markdown-артефакты при действующем захвате. Для создания используется ожидание отсутствующего ключа, для обновления и удаления — прочитанная версия. Если результат изменился после чтения, KOS сообщает о конфликте и сохраняет более новую редакцию. Список артефактов задачи выдаётся по возрастанию ID порциями до 100 результатов (по умолчанию 50). При наличии следующей порции ответ содержит `pagination.next_after_id`; продолжить чтение можно командой `kos task artifact list TASK_ID --after-id ID`, при необходимости с `--limit N`. Содержимое отдельного артефакта по-прежнему доступно по его ключу. Артефакты и краткий итог остаются при освобождении или повторном захвате задачи.

Если нужно сверить состояние без повторного чтения документов, `kos task show ID --brief` возвращает состояние и текущий шаг, связи, ключи и версии артефактов с указанием источников, причины недоступности и указатели продолжения страниц. Длинные тексты постановки, итогов и документов отсутствуют. Полный просмотр остаётся доступен без флага, а отдельный документ — по ключу. Краткое чтение выполняет сервер: CLI не получает и не обрезает полный текст самостоятельно.

Когда нужны только сведения о выбранной задаче, `kos task show ID --state` (API `view=state`) показывает её ID, название, состояние, номер текущего шага, рассчитанную сервером доступность с причинами, ключи и версии собственных результатов. Списки связей, чужие результаты и тексты не возвращаются. Результаты выдаются по возрастанию ID порциями: `pagination.complete` показывает, закончена ли выдача, а `pagination.next_after_id` позволяет запросить следующую порцию через `--artifact-after-id ID`; размер задаётся `--context-limit N` (по умолчанию 50, максимум 100). Этот вид не меняет обычный просмотр и `--brief`. При необходимости полного контекста или текста отдельного результата пользователь запрашивает их отдельно.

После успешного `kos task artifact put TASK_ID KEY --brief` ответ подтверждает ID, ключ и новую версию результата, не повторяя его текст; без флага ответ содержит текст, как прежде. Краткий ответ не меняет требования к захвату, ожидаемому шагу и версии; при конфликте возвращается обычная машиночитаемая ошибка. `--help` на уровнях `kos`, раздела и команды показывает синтаксис в JSON без проекта, сервера и обязательных аргументов. Ошибка неизвестной команды перечисляет доступные варианты, в том числе `task step` и `task advance`.

## Завершение и исключения

`release` возвращает задачу в `planned`, `complete` переводит её в `done` только на последнем шаге; обе операции могут сохранить краткий итог. Шаг меняется отдельной операцией владельца и сохраняется при освобождении. Завершённая задача больше не доступна для захвата, а её результаты остаются доступны для чтения. Переоткрытие — отдельное действие; оно не разрешается, если зависящая от неё работа уже началась или завершилась.

Если ответ на изменяющий запрос потерян, CLI сообщает о неопределённом результате и предлагает проверить состояние перед повтором. Статус `done` означает заявление исполнителя о готовности, а не автоматическое подтверждение тестов, ревью или публикации в GitHub. KOS не управляет файлами и действиями агента вне трекера.
