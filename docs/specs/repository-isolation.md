# KOS Repository Isolation

## Repository Scope

One central KOS installation may serve multiple Git repositories. Every repository-owned record and operation is scoped by immutable `repository_id`. The API resolves and authorizes that scope before mutation and never trusts a supplied filesystem path as the sole proof of identity. Registration independently verifies the canonical Git common directory and trusted publication settings and is defined by [Central Persistence](central-persistence.md). [ADR-0001](../decisions/0001-central-rest-api.md) owns the multi-repository architecture rationale.

## Task Isolation

Every task whose workflow changes repository files uses a dedicated branch derived from its repository-specific public number, such as `kos/task-KOS-000123`, a dedicated Git worktree, and a worktree allocation recorded in task state.

Allocation is a recoverable protocol:

1. The CLI atomically reserves a unique canonical branch name and worktree path with the active attempt's fencing token.
2. `kos-repository` materializes only that reservation.
3. The CLI confirms allocation after verifying repository identity, Git common directory, branch, and canonical path.

An incomplete reservation is reconciled after lease expiry. An existing worktree cannot be adopted without proof that it belongs to the same reservation.

The state service accepts only a task-derived branch and a lexically canonical absolute reservation path. It does not inspect that path or execute Git. The repository adapter remains responsible for filesystem canonicalization, symlink containment, Git common-directory identity, branch, HEAD, and cleanliness before an effect. Confirmation compares the adapter's common-directory digest with SHA-256 over the repository's persisted canonical UTF-8 common-directory path and records the observed HEAD.

After an expired attempt is reconciled, the next claim transfers an unresolved reservation's current owner and fencing token without changing its allocation or treating the worktree as confirmed. A clean reconciliation with an observed HEAD can confirm a reserved allocation. An absent observation leaves an unmaterialized reservation available for the owning attempt to reuse, and completes release only after materialization. Dirty and mismatched observations preserve the allocation and require explicit resolution; they never authorize adoption or removal.

## Git Ownership

`kos-repository` is the only skill allowed to perform mutating Git operations, including worktree creation or removal, commit, fetch, rebase, and push. The CLI persists and protects worktree reservations, publication intents, and generic commit/fetch/rebase intents but does not execute Git commands. During a workflow-step session, the generic executor may send an attempt-bound typed effect request to the lease-owning orchestrator. The orchestrator validates and durably prepares it, invokes `kos-repository`, reconciles its typed success, failure, or unknown observation, and returns that result before the executor finalizes its result manifest.

Before every operation, `kos-repository` validates repository identity, reservation, fencing token, expected branch and HEAD, and worktree cleanliness against the operation's preconditions. Detailed adapter requirements are defined by the [architecture rules](../rules/architecture.md).

The local `kos-repository` adapter accepts only its closed version 1 JSON documents for `materialize`, `observe`, `remove`, and `commit`. Each request carries the registered repository identity and canonical common directory, the current reservation identity and fencing token, and an explicit expected SHA-1 commit. Materialization requires a `reserved` snapshot and verifies that the registered base ref still names the expected commit before creating the task branch. Removal requires `release_pending`. Commit requires a `confirmed` snapshot whose task-derived branch, marker, canonical worktree path, and exact HEAD all match. The runtime-facing skill that supplies these documents is a separate integration boundary.

An existing linked worktree is proof of an idempotently completed materialization only when its canonical path, common directory, branch, HEAD, and adapter-owned reservation marker all match. A pre-existing branch or unmarked worktree is mismatched and is neither adopted nor removed. The marker identifies the durable allocation rather than its temporary attempt owner, so ownership transfer changes the request fencing token without rewriting Git metadata.

Adapter observations bind repository, reservation, fencing token, path, branch, state, and observed Git identity into canonical SHA-256 evidence. Cleanliness includes staged, unstaged, untracked, and ignored files and unfinished merge, cherry-pick, revert, rebase, sequencer, or bisect state. Any such state is dirty. Existing paths and Git metadata must resolve canonically without symlinks; an absent worktree's parent must already exist and be canonical.

A commit starts only with an index equal to the expected HEAD and no unfinished Git operation. Its paths are unique, lexically and filesystem canonical, repository-relative exact regular files; directories, tracked or filesystem symlinks, path aliases, overlapping scopes, traversal, and pathspec magic are rejected. Git treats accepted paths literally. The adapter uses literal `git check-attr -z filter` for every requested path initially, immediately before reading the worktree diff, and after staging; any configured filter is rejected. It verifies `expected_diff_digest` over the exact bytes from `git diff --binary --full-index --no-ext-diff --no-textconv <expected-head> -- <byte-sorted-paths>`.

The adapter seeds an isolated temporary index from the expected HEAD without using `git add`. For each present path it opens the exact canonical reservation root with `O_NOFOLLOW|O_DIRECTORY`, proves that `/proc/self/fd/<root-fd>` resolves to that reservation path, and keeps the root descriptor open. It then traverses every component relative to its held parent descriptor through `/proc/self/fd/<parent-fd>/<component>`, opening intermediates with `O_NOFOLLOW|O_DIRECTORY` and the final component with `O_NOFOLLOW` and a regular-file requirement. All parent descriptors remain open until the final file is hashed. A component swapped to an outside symlink therefore fails at its descriptor-relative open even if the attacker restores the pathname before any later check. Once opened, the same contained final descriptor is passed directly to `git hash-object --no-filters -w --stdin`, so later pathname changes cannot redirect the read.

The resulting blob is added to the temporary index with an explicit mode, OID, and literal path using `git update-index --add --cacheinfo`; an approved tracked regular-file deletion is removed explicitly with `git update-index --force-remove`. This prevents clean and process filter execution during staging even if attributes or configuration change after the initial policy check. File modes match normal Git behavior: executable bits are honored when `core.filemode` is true, while an existing tracked mode is preserved and a new file defaults to non-executable when it is false. `expected_index_digest` remains authoritative over NUL-terminated, byte-sorted `<mode> <blob-oid>\t<path>` stage-zero entries. The complete temporary tree may differ from the expected HEAD at exactly every requested path and nowhere else; the staged result must be nonempty. If Linux descriptor traversal or `/proc/self/fd` proof is unavailable, staging fails safely.

The caller's commit message must not contain a parsed `KOS-Task` trailer. The adapter appends exactly one `KOS-Task: <task-number>` trailer, creates a commit object from the explicit verified tree using repository-local author and committer identity, and verifies its expected parent, tree, and sole task trailer. It advances only the exact reserved branch by comparing its current value with the expected HEAD. A successful compare-and-swap response is definitive and is never downgraded by later index maintenance or branch observation. A failed or raised update is observed before classification: the expected commit is success, an unavailable observation is uncertain, the unchanged expected HEAD is a rejected update, and another commit is a branch-movement conflict. Temporary-index mismatch or commit-object failure never changes the real index. After success, the adapter attempts to reconcile only requested entries in the real index under Git's index-lock convention, preserving unrelated entries staged concurrently. This refresh is best effort and cannot change commit success: if another process already owns the lock, the adapter neither removes nor overwrites that lock and leaves the real index byte-identical, which may require a later refresh to align requested entries with the new HEAD. Worktree files are never reset. A success returns the observed commit SHA and a canonical SHA-256 evidence digest binding the repository, reservation and fencing snapshot, path, branch, parent, tree, commit, byte-sorted paths, requested diff and index digests, and task number. Failures use only the adapter schema's closed safe errors and never include raw Git diagnostics or supplied paths.

Repository mutations are serialized for their complete validation and effect by a lock in the registered common directory. Git runs with bounded time, argument arrays, prompts and pagers disabled, global and system configuration excluded, hooks, editors, signing, external diff, replacement objects, filesystem monitors, and lazy object fetching disabled. Version 1 rejects repositories whose object format is not SHA-1. Cleanup unlocks an adapter-owned worktree only immediately before ordinary non-forced `git worktree remove`; it never recursively deletes the path or deletes the task branch.

Terminal cleanup is a separate idempotent two-phase operation. An observed clean worktree with its confirmed HEAD moves the reservation to `release_pending`; only a later `absent` observation atomically detaches it from the task and marks it `released`. A crash after removal is recovered by reconciling that absence. KOS never automatically removes a dirty or mismatched worktree, and released reservation history remains immutable while no longer occupying its active uniqueness keys.
