# Локальный трекер задач для AI-агентов

## Спецификация расширенного MVP

- Версия документа: 0.2
- Дата: 29 сентября 2026 года
- Состав первого этапа: Rails-приложение с SQLite и REST API; Ruby CLI-гем.
- Статус документа: свод согласованной концепции и требований к расширенному MVP. Предлагаемые технические соглашения и ещё не утверждённые значения отдельно отмечены в разделе 17.

**Главный принцип:** небольшое работающее решение, которое можно расширять по мере появления потребностей. Не строить заранее универсальный оркестратор агентов, движок workflow или систему управления документами.

## 1. Назначение и принципы

Приложение хранит задачи разработки программного обеспечения и предоставляет AI-агентам единый способ планировать работу, получать необходимый контекст, безопасно захватывать задачи и сохранять результаты.

Сервер является источником истины о задачах, зависимостях, захватах и артефактах. CLI предоставляет удобный интерфейс к серверу и определяет текущий проект по Git-репозиторию.

### 1.1. Основные принципы

- Простой расширяемый MVP. Реализовывать текущие сценарии, а не инфраструктуру для всех будущих возможностей.
- Соглашения вместо настройки. Проект определяется из Git; обычные операции не требуют файлов конфигурации в каждом репозитории.
- Серверные гарантии. Доступность задачи, владение и допустимость изменений проверяются сервером, а не только CLI.
- Минимум обращений. Захват задачи возвращает контекст, необходимый для начала или продолжения работы.
- Универсальность. Контракт не зависит от OpenCode, модели AI или конкретной среды запуска агента.
- Явные отношения. Группировка, зависимости, владение и результаты — разные понятия. Тип задачи не вызывает скрытых изменений графа.

### 1.2. Что является задачей

Обычная задача разработки — законченное изменение: фича, исправление или другой самостоятельный результат. В перспективе внутри неё выполняется весь цикл: планирование и спецификация, реализация и тесты, документация, ревью, публикация.

Эти действия являются шагами задачи, а не автоматически отдельными подзадачами.

Задачей также может быть работа без изменения кода, например подготовка верхнеуровневой спецификации и декомпозиция эпика. Её результат — документы и сформированный набор задач.

## 2. Границы первого MVP

### 2.1. Входит в первый этап

1. Локальное Rails-приложение с SQLite и JSON REST API.
2. CRUD проектов, групп задач и задач.
3. Зависимости между задачами и определение доступной работы.
4. Атомарный захват, продление lease, освобождение и завершение задачи.
5. Повторный захват после истечения lease.
6. Хранение текстовых артефактов задач в БД.
7. Получение задачи вместе с её контекстом.
8. Ruby CLI-гем из репозитория проекта на GitHub.
9. Автоматическое определение проекта через Git remote и возможность явного указания проекта.
10. Автоматизированные тесты, включая конкурентные операции и восстановление после ошибок.
11. Определения workflow с последовательностью шагов, текущий шаг задачи и адресный контекст шага для исполнителя.
12. Компактный маршрут шага при захвате, явное продвижение под действующим захватом.

### 2.2. Не входит в первый этап

- Skills и готовые интеграции с агентными средами не входят в серверный MVP; отдельный клиентский пакет OpenCode согласован для PLAN-014.
- Автоматическая оценка качества артефактов, исполнение шагов и проверка полноты результата сервером.
- Запуск агентов, субагентов и команд разработки сервером. Установочные skills и конфигурация OpenCode относятся к отдельному пакету PLAN-014, не к Rails API.
- Создание worktree и веток, коммиты, push, merge и GitHub API.
- Синхронизация с GitHub Issues или другими трекерами.
- Автоматическая публикация результатов.
- UI, MCP-сервер, пользователи, роли и многопользовательская авторизация.
- Синхронизация БД через Git, офлайн-репликация и распределённая установка.
- Вложенные группы, несколько групп у одной задачи и отдельная иерархия подзадач.
- История редакций артефактов, файловые вложения и двусторонняя синхронизация документов с Git.
- Приоритеты, сроки, оценки трудоёмкости, уведомления и фоновый планировщик.

Чтение Git remote для определения проекта входит в MVP. Это не означает реализацию Git-workflow.

Отдельно согласованный PLAN-018 добавляет клиентские инструкции `/kos-init`, `/kos-update`, `/kos` для OpenCode: агент обновляет локальный checkout из GitHub, CLI и файлы интеграции только при безопасном fast-forward без потери локальных изменений. Это операция обслуживания установки, а не Git-workflow задач или серверная возможность. Миграция существующей БД и перезапуск сервера требуют двух отдельных явных разрешений; автоматическая миграция не следует из обновления файлов.

Отдельный клиентский пакет PLAN-019 добавляет два OpenCode skill для явно запрошенных операций Git и GitHub CLI. Они направляют агента к локальной справке `git`/`gh` за командами вне примеров, требуют учитывать правила проекта и поручение на публикацию; способ публикации выбирает проект. Это не команды Rails API или CLI KOS.

Клиентские инструкции PLAN-020 добавляют worktree для задач разработки в OpenCode: после захвата агент определяет необходимость по явной постановке или правилам целевого проекта, а не по произвольному `kind`. Правила целевого проекта определяют имена, расположение, базовую ветку и способ публикации. Если имён и расположения в них нет, короткое имя целевого Git-проекта и ID задачи дают ветку `<project>/task-<ID>` и соседний каталог `<project>-task-<ID>`; проектом может быть не KOS. На повторном входе используется проверенный существующий worktree; главный агент и исполнители работают в нём. После подтверждённой публикации по правилам проекта и проверки чистоты worktree агент может удалить его без принуждения. При конфликте, неясном результате или незавершённой публикации каталог сохраняется для восстановления. Сервер не контролирует внешнее состояние Git; `complete` не подтверждает публикацию.

Клиентский skill проектной документации применяется при явном вызове в шаге документации или нормативной спецификации Brief. Для затронутых пользовательских доменов документация реализованного поведения обязательна: путь задают правила целевого проекта, иначе используется `docs/`. Если проект требует OKF v0.2, концепты соответствуют этому формату; иначе сохраняется принятый формат проекта. При отсутствии пользовательского изменения исполнитель проверяет затронутые документы и фиксирует причину отсутствия правок. Противоречивые или запрещающие публикацию проектные правила требуют уточнения. Документы описывают сценарии, наблюдаемые результаты и ограничения; артефакты KOS их не заменяют. Rails API и CLI остаются прежними.

Единственные общие клиентские workflow Brief v1, Execution v1 и Fix v1 используют это правило. Brief явно вызывает `kos-project-docs`, создаёт или обновляет Markdown-документ утверждённого требуемого поведения и публикует его до завершения задачи. Правила проекта определяют формат и расположение; при отсутствии заданного пути используется `docs/`. Текущий прогресс отражают задачи KOS и их результаты, без второго вручную обновляемого файла статусов. Повторный seed может заменить только неиспользуемое определение; определение с задачами не заменяется и не удаляется.

PLAN-026 утверждает клиентский сценарий OpenCode без ручного ID: `kos session new` локально выдаёт случайный непрозрачный ID в JSON без Git и API. Основной агент получает его один раз на новую рабочую беседу, повторно использует в ней и самостоятельно загружает оркестратор при запросе работы с KOS; `/kos` необязателен. В Plan можно обсуждать Brief без записи, сохраняющие действия — в Build после согласования. В продолженной беседе используется прежний ID и `current`; новая беседа может восстановить действующий захват по прежнему `session_id` только после явного подтверждения остановки старого агента и проверки задачи, шага, срока и worktree. Без подтверждения ожидают истечения lease либо освобождения из прежней беседы. После истечения новая беседа берёт новый ID и новый claim с сохранённым шагом и результатами. Rails API не изменяется; plugin и скрытое хранение ID не добавляются.

PLAN-029 утверждает клиентский путь от ссылки на KOS до установленного OpenCode и начала работы в новом проекте. README направляет агента через безопасную установку и проверку; глобальная установка не меняет произвольные проекты. Для явно выбранного проекта агент бережно добавляет инструкции KOS в его `AGENTS.md`. При отсутствии папки или репозитория агент обсуждает расположение, реальный адрес `origin` и способ подготовки удалённого репозитория с человеком в контексте этого проекта; проверяет публикационный маршрут и базовый коммит, прежде чем создать Brief по общему workflow. Планируемое имя папки или фиктивный remote не заменяют реальный репозиторий. Подготовка репозитория согласуется отдельно от утверждения требований Brief. В обращении к человеку используются его язык либо язык из `AGENTS.md`, варианты выбора нумеруются цифрами с просьбой ответить одной цифрой. Оркестратор продолжает восстановимые действия без лишних остановок, спрашивает человека только при необходимом решении или действии, а после проверенного завершения сообщает ход работы, наблюдаемый результат, место публикации, следующую задачу и действия человеку. Потеря lease, неопределённый исход и отсутствие доступных задач не объявляются завершением; сервер не гарантирует выполнение внешних действий или непрерывность работы процесса.

### 2.3. Развёртывание

Сервер работает локально и доступен только через loopback-интерфейс. SQLite хранится на постоянном локальном диске машины сервера. Клиенты обращаются к API, а не открывают файл базы.

Для повседневной локальной установки сервер запускается вручную контейнером Docker через `mise run kos` в переднем плане, с сохранением существующей SQLite в каталоге хоста. Снаружи контейнера доступен только `127.0.0.1:3137`; контейнер не запускается автоматически как пользовательский сервис. CLI по умолчанию подключается к этому адресу. Это согласованное изменение ранее принятого порта 3000 для исключения конфликта с другими Rails-приложениями (PLAN-031).

Не требуется Redis, отдельный сервис блокировок или фоновые задания для освобождения просроченных задач.

Отсутствие аутентификации допустимо только для этой локальной модели. Настоящую защиту от недоверенных локальных процессов MVP не обещает; сетевое развёртывание потребует отдельного решения.

## 3. Термины и ответственность компонентов

| Термин | Значение |
| --- | --- |
| Проект | Область задач, соответствующая одному Git-репозиторию |
| Группа задач | Общая цель и набор задач; первый тип — epic |
| Задача | Единица выполнения с конкретным результатом |
| Тип задачи | Идентификатор характера работы; workflow задаётся отдельно |
| Шаг | Этап workflow с инструкцией, входами, результатами и маршрутом исполнителя |
| Зависимость | Требование завершить одну задачу до начала другой |
| Сессия | Стабильный непрозрачный идентификатор исполнителя, переданный клиентом |
| Захват, claim | Конкретная попытка владения задачей |
| Lease | Ограниченный по времени срок действительности захвата |
| Артефакт | Именованный текстовый результат работы над задачей |
| Контекст задачи | Постановка, группа, результаты, зависимости и сведения для продолжения работы |

| Компонент | Ответственность |
| --- | --- |
| Rails API | Состояние, валидация, зависимости, выбор работы, захваты, артефакты |
| Ruby CLI | Git-идентификация проекта, ввод и вывод, передача сессии, вызовы API |
| Агент или вызывающая среда | Работа над задачей, сохранение результатов, вызов продления, заявление о завершении |
| Skills OpenCode (PLAN-014) | Клиентские инструкции по использованию CLI и выполнению шагов |

CLI не дублирует серверный алгоритм определения доступности и не выполняет захват через клиентскую последовательность «найти свободную задачу → обновить её».

## 4. Модель данных

Расширенный MVP содержит шесть основных таблиц:

- `projects`
- `task_groups`
- `tasks`
- `task_dependencies`
- `task_artifacts`
- `workflows` (расширение MVP)

Основные связи:

```text
Project
  ├── TaskGroup
  ├── Workflow
  └── Task
        ├── Workflow → шаги и инструкции
        ├── optional TaskGroup
        ├── TaskDependency → другая Task
        └── TaskArtifact
```

Все сущности имеют внутренний серверный `id`. Основные записи имеют `created_at` и `updated_at`. Внешние ключи и уникальность критических сочетаний обеспечиваются БД, а не только валидациями приложения.

### 4.1. Project / projects

| Поле | Назначение |
| --- | --- |
| id | Стабильный внутренний идентификатор |
| repository | Уникальный канонический ключ Git-репозитория |
| name | Отображаемое название; по умолчанию из имени репозитория |

Пример `repository`: `github.com/owner/repository`.

Название не является идентификатором: репозитории разных владельцев могут иметь одинаковое короткое имя.

### 4.2. TaskGroup / task_groups

| Поле | Назначение |
| --- | --- |
| id | Идентификатор группы |
| project_id | Проект |
| kind | Тип группы; в MVP только `epic` |
| title | Название |
| description | Общая цель, исходные требования и границы |

У группы нет хранимого статуса, полей захвата или собственного workflow.

В ответах можно возвращать вычисляемые `completed`, `tasks_total`, `tasks_done`, `tasks_in_progress`.

Готовность группы:

```text
completed = задач больше нуля AND все задачи имеют status = done
```

Пустая группа не завершена. Добавление незавершённой задачи автоматически меняет вычисляемую готовность. Завершённость означает выполнение всех зарегистрированных задач, а не серверную проверку достижения общей цели.

### 4.3. Task / tasks

| Поле | Назначение |
| --- | --- |
| id | Идентификатор задачи |
| project_id | Проект |
| task_group_id | Необязательная группа |
| kind | Тип задачи; строковый идентификатор |
| title | Название |
| description | Постановка, границы и ожидаемый результат |
| status | `planned`, `in_progress` или `done` |
| work_summary | Краткое текущее состояние и итог работы |
| workflow_id | Обязательная ссылка на неизменяемое проектное или общее определение workflow |
| current_step | Позиция текущего шага (начинается с 0) |
| session_id | Сессия текущего или последнего ещё не очищенного захвата |
| claim_id | Идентификатор конкретного захвата |
| claimed_at | Время начала захвата |
| lease_expires_at | Время окончания lease |

`kind` задачи и `kind` группы независимы. Поле `type` не используется.

`description` — постановка работы, `work_summary` — краткая запись для передачи работы, артефакты — подробные результаты. Полей `specification`, `review_report` и подобных в `tasks` нет.

Новая задача создаётся в `planned`, без захвата. Задача может не входить в группу. Группа и задача должны принадлежать одному проекту. Проектное определение workflow должно принадлежать проекту задачи; общее доступно всем проектам. Перенос задач между проектами в MVP не поддерживается.

Тип задачи не выбирает workflow автоматически. Новые задачи создаются с явным `workflow_id`; локальные старые задачи разрешено очистить при переходе на расширенный MVP.

### 4.4. TaskDependency / task_dependencies

| Поле | Назначение |
| --- | --- |
| task_id | Задача, которая ожидает |
| blocking_task_id | Задача, завершение которой требуется |

`A blocked_by B` означает: A нельзя начинать, пока B не завершена.

Обязательные ограничения:

- обе задачи принадлежат одному проекту;
- задача не зависит от самой себя;
- пара (`task_id`, `blocking_task_id`) уникальна;
- граф не содержит циклов;
- изменение графа не оставляет промежуточно некорректное состояние.

Связи могут пересекать границы групп внутри проекта. Завершение блокирующей задачи не удаляет зависимость: связь сохраняет информацию о происхождении входных результатов.

### 4.5. TaskArtifact / task_artifacts

| Поле | Назначение |
| --- | --- |
| id | Идентификатор артефакта |
| task_id | Задача-владелец результата |
| key | Устойчивое имя результата внутри задачи |
| content | Markdown-текст |
| lock_version | Версия для защиты от конфликтующего обновления |

Пара (`task_id`, `key`) уникальна на уровне БД. В пределах задачи хранится одна текущая редакция результата с данным ключом.

Примеры ключей:

- `specification`
- `implementation_plan`
- `test_report`
- `review_report`

Ключ обозначает конкретный ожидаемый результат, а не обязательно глобальный тип документа. Два разных отчёта используют разные ключи. Шаг может перечислять ожидаемые выходы, но сервер не требует их наличия для перехода.

Шаблоны не хранятся в этих записях. Отдельные таблицы шагов, template_id и полиморфные владельцы артефактов не вводятся.

### 4.6. Workflow и шаги (расширение MVP)

`workflows` могут принадлежать проекту или быть общими для всех проектов (`project_id: null`); каждая запись имеет `id`, `project_id`, `name`, упорядоченное непустое определение шагов и timestamps. Определение шага содержит непустые `name` и `instructions`, маршрут `executor: main | subagent`, для субагента обязательный `model_tier: standard | advanced`, список селекторов входных артефактов и список ключей выходов. Селектор указывает `source: task | blockers` и `key`; `blockers` означает только непосредственные блокирующие задачи с явным сохранением источника каждого совпадения. Отсутствие входа сообщается явно, а не создаёт пустой результат. Запись определения нельзя менять после создания; новую редакцию создают новым workflow. Неиспользуемое общее seed-определение разрешено удалить и создать заново под тем же именем. Удаление используемого workflow запрещено. Задача может использовать общее или своё проектное определение; чужое проектное определение запрещено БД.

`current_step` — позиция шага для исполнения (нумерация с нуля). Она начинается с 0, меняется только явной операцией владельца и сохраняется при release, повторном захвате и истечении lease. На последнем шаге обычное продвижение невозможно; `complete` завершает задачу, только если она на последнем шаге. Сервер не проверяет содержание выходных артефактов. Работа над задачей без workflow после перехода не поддерживается.

Три общих определения Brief, Execution и Fix устанавливаются идемпотентным seed на совместимую БД. Определения назначенных задач неизменяемы; seed может заменить только определения без задач. Brief выполняет главный агент в диалоге: он получает согласие человека на высокоуровневые решения и план **до** записи артефактов, создания группы или задач. После согласования он сохраняет высокоуровневые `requirements`, `specification`, `implementation_plan`, создаёт одну или несколько planned-задач Execution (при эпике — группу) с явной зависимостью от Brief и записывает их ID и связи в `planning_report`. Конкретная реализация уточняется на шаге планирования каждой новой задачи. Execution включает уточнение плана, реализацию и тесты (`advanced`), независимое ревью другим исполнителем `advanced` с исправлением обязательных замечаний на том же шаге, документацию и подтверждённую публикацию (`standard`). Fix начинается с диагностики и `root_cause_report` по описанию задачи без обязательного Brief, далее проходит аналогичный цикл. Если нет пользовательского изменения, шаг документации проверяет затронутые документы и фиксирует причину отсутствия правок. Публикация является поручением соответствующего шага, не требует отдельного разрешения на каждом выполнении, но следует правилам целевого проекта; главный агент подтверждает результат до `complete`. Инструкции направляют агента продолжать работу без лишних пауз, обращаясь к человеку только при блокере или необходимом решении. Все эти условия являются инструкциями клиентского workflow, а не серверной автоматической проверкой качества, согласия или публикации.

Brief v1 обсуждает значимые неоднозначности, альтернативы и крайние случаи, фиксирует причины решений и проверяемые критерии. Значимые вопросы имеют сквозные номера внутри Brief, ответы либо явный статус открытого вопроса. Для существенных требований рекомендуются человекочитаемые идентификаторы от обозначения проекта и ID задачи Brief (`shop-task-42/AC-01` и аналогично `REQ`, `DEC`, `Q`); коллизии имён проектов снимаются уточнением владельца или хоста. Связи критериев с задачами и проверками фиксируются без разметки каждой строки исходного кода. Утраченное согласие повторно уточняется. Brief сохраняет снимки в KOS, создаёт заблокированные задачи Execution v1, документирует утверждённое требуемое поведение в проектном файле и на последнем шаге публикует файл и подтверждает назначение до `complete`. Публикация обязательна; при запрете проектом или неясном результате исполнитель остаётся на шаге и запрашивает решение либо сверяет состояние. Планирование Execution v1 и Fix v1 уточняет вопросы, решения, критерии, крайние случаи и проверки для конкретной задачи со сквозной нумерацией её вопросов, но не меняет утверждённую норму без согласия. Реализация и ревью соблюдают архитектуру, стиль, безопасность, верхнеуровневые требования и проверки целевого проекта. Независимое ревью классифицирует проблемы как высокие, средние и низкие; высокие и средние обязательно исправляются с повторной проверкой и ревью, низкие могут остаться с обоснованием. Документация описывает фактическое пользовательское поведение затронутых доменов; после поздних изменений затронутые проверки и, при изменении проверенного поведения, независимое ревью повторяются до публикации. Fix не требует Brief. Сервер не выводит статус реализации нормы из документов и не проверяет качество ревью или факт публикации.

Компактный ответ `claim`/`claim-next`/`current` по запросу оркестратора возвращает маршрут шага и сведения о захвате без содержимого документов. Исполнитель (в том числе главный агент для шага `main`) по ID задачи отдельно запрашивает пакет шага: инструкцию, текущий маршрут, входные артефакты с задачей-источником и `lock_version`, явно отмеченные отсутствующие входы и ожидаемые ключи выходов. Чтение не требует захвата. Пакет возвращает все совпадающие входы без скрытой обрезки и может быть объёмным; если появится предел, ответ должен явно сообщать о неполноте и способе продолжения. Запись результатов по-прежнему требует действующего `claim_id` всей задачи. В OpenCode оркестратор передаёт субагенту только отпечаток claim и идентификатор сессии; CLI самостоятельно запрашивает действующий токен и отправляет его существующему API, не раскрывая его в выводе агента. Запуск агента и сопоставление `standard`/`advanced` конкретным моделям выполняются вне сервера KOS, в клиентской интеграции OpenCode PLAN-014.

## 5. Идентификация проекта и соглашения Git

### 5.1. Определение текущего проекта

При отсутствии явного параметра CLI получает адрес `origin` текущего репозитория и преобразует поддерживаемый адрес в канонический ключ.

Например:

```text
git@github.com:owner/project.git
https://github.com/owner/project.git

→ github.com/owner/project
```

Правила нормализации должны быть едиными и покрыты тестами. Не допускается сохранять пароли или access tokens из URL. Нельзя безусловно менять регистр пути для произвольного Git-хостинга.

Разные клоны и worktree с одним каноническим remote относятся к одному проекту. Локальное имя каталога не является идентификатором. Форк с другим remote по умолчанию является другим проектом.

Если репозиторий или `origin` отсутствует либо адрес не поддерживается, CLI выдаёт понятную ошибку и предлагает явное указание проекта. Не угадывать проект по директории и не подключаться к GitHub API для поиска соответствия.

### 5.2. Явное указание

CLI должен позволять указать канонический ключ проекта явно. Это необходимо для работы вне репозитория и с remote, которые невозможно однозначно нормализовать.

Переименование репозитория отражается явным обновлением существующего проекта. Автоматическое обнаружение переименований не требуется.

### 5.3. Без лишнего запроса на поиск ID

Scoped-операции API должны принимать канонический ключ проекта. Сервер сам разрешает его во внутренний `project_id`; CLI не обязан перед каждым действием отдельно искать ID проекта.

При создании первого проектного workflow или группы проект можно автоматически создать по переданному каноническому ключу. Общее определение создаётся без проекта и может использоваться задачами разных проектов. Для задачи необходим доступный ей workflow, поэтому он создаётся раньше задачи; создание задачи с общим workflow также атомарно регистрирует отсутствующий проект. Чтение, поиск и захват никогда не создают проекты. Создание проекта и основной записи должно быть атомарным; повторные обращения не создают дубликаты.

## 6. Группы и декомпозиция

### 6.1. Группа не является задачей

Группу не захватывают и не завершают отдельной командой. Планирование выполняется обычной задачей, входящей в эту группу.

Пример:

```text
Группа: Авторизация
  kind: epic

  #10 Спецификация и декомпозиция авторизации
      kind: decomposition
      artifacts: specification, implementation_plan

  #11 Вход по электронной почте и паролю
      blocked_by: #10

  #12 Восстановление пароля
      blocked_by: #10, #11
```

Задача декомпозиции захватывается и выполняется по общим правилам. Её результаты: верхнеуровневая спецификация, созданные задачи и установленные зависимости.

### 6.2. Где находится верхнеуровневая спецификация

Она является артефактом задачи декомпозиции, например `#10/specification`.

Группа хранит исходную цель и описание, но не вторую редактируемую копию этого документа. Спецификация отдельной фичи хранится в самой задаче фичи и уточняет общий замысел, а не дублирует его.

### 6.3. Доступность задач во время планирования

Создаваемые при декомпозиции задачи сразу получают зависимость от задачи планирования. API обязан поддерживать создание задачи вместе с группой и зависимостями в одной транзакции.

Недопустим обязательный клиентский сценарий:

```text
создать доступную задачу → отдельным запросом заблокировать её
```

Планировщик сначала сохраняет необходимые результаты и весь подготовленный набор задач, затем завершает задачу декомпозиции. Только после этого её зависимые задачи становятся доступными при выполнении остальных условий.

Тип `decomposition` не блокирует группу автоматически. Сервер гарантирует соблюдение заданных зависимостей, но не угадывает забытые отношения и не оценивает полноту плана.

### 6.4. Повторное планирование

Уточнение ранее принятого плана может быть новой задачей с новыми артефактами и явными зависимостями для затронутой работы. Группа не переводится в специальный режим планирования.

Сервер не выбирает автоматически «самую новую спецификацию группы». Исполнитель получает конкретные результаты задач, на которые явно опирается его работа.

## 7. Статусы, доступность и изменение задач

### 7.1. Статусы

| Статус | Смысл |
| --- | --- |
| planned | Задача запланирована, действующего захвата нет |
| in_progress | Работа началась; захват может быть действующим или просроченным |
| done | Исполнитель заявил, что результат задачи получен |

`blocked`, `ready` и `lease_expired` — вычисляемые свойства, а не дополнительные статусы.

### 7.2. Доступная задача

Задача доступна для нового захвата, если одновременно:

1. Она принадлежит выбранному проекту и соответствует фильтрам выбора.
2. Её статус — `planned` либо `in_progress` с просроченным lease.
3. Нет действующего захвата.
4. Все непосредственные блокирующие задачи имеют статус `done`.

Наличие группы не создаёт дополнительных неявных условий. В частности, задача не ждёт вычисляемого завершения своей группы.

Список `ready` является снимком для ознакомления, а не обещанием успешного последующего захвата.

### 7.3. Операции состояния

| Операция | Результат |
| --- | --- |
| claim / claim-next | Задача становится `in_progress`, устанавливается новый захват |
| renew | Продлевается действующий lease, статус не меняется |
| release | Задача возвращается в `planned`, захват очищается |
| complete | Задача становится `done`, захват очищается |
| reopen | Завершённая задача явно возвращается в `planned` |

Обычный `update` не принимает произвольный `status` и поля захвата. Их нельзя использовать для обхода соответствующих операций.

Освобождение, повторный захват и повторное открытие не удаляют артефакты и `work_summary`.

### 7.4. Изменение плана и удаление

Предлагаемые консервативные правила MVP:

- Зависимости, тип и группу меняют у задач в `planned`; не менять структурные условия уже выполняющейся задачи без её освобождения.
- Изменения постановки выполняющейся задачи и её прогресса требуют действующего захвата.
- Завершённую задачу нельзя незаметно вернуть в работу обычным редактированием.
- `reopen` отклоняется, если от результата уже началась или завершилась зависимая работа. Не выполнять каскадное переоткрытие графа.
- Задачу нельзя удалить при действующем захвате или наличии задач, которые от неё зависят.
- Явное допустимое удаление задачи может удалить её собственные артефакты и её связи с блокерами, но не другие задачи.
- Непустую группу и проект с группами, задачами или workflow удалить нельзя. Каскадное удаление проекта и команды `force` не входят в MVP.

Все проверки выполняются сервером. Окончательное поведение `reopen` отмечено среди технических соглашений раздела 17.

## 8. Сессии, захваты и lease

### 8.1. Идентичность

`session_id` — стабильная строка, полученная от вызывающей среды. Сервер не разбирает её внутреннюю структуру и не хранит отдельную сущность OpenCode.

В OpenCode агент может один раз запросить случайный ID локальной командой CLI `kos session new` и удерживать его в контексте беседы. Существующие клиенты могут передать собственный `session_id` как прежде; команда не меняет серверную идентичность.

Все вызовы одной сессии используют одно значение. Разные независимо работающие сессии должны иметь разные значения. Нельзя генерировать новую сессию при каждом запуске CLI или использовать один общий идентификатор на весь репозиторий.

`claim_id` выдаётся сервером и идентифицирует конкретный захват, а не сессию. Каждый новый захват, включая повторный той же сессией после истечения lease, получает новый уникальный `claim_id`.

Детерминированная производная только от `session_id` не подходит. Старые запросы не должны становиться действительными после нового захвата той же сессией.

### 8.2. Действительность

Захват действителен только при одновременном выполнении условий:

```text
task.status == in_progress
переданный claim_id совпадает с текущим
task.lease_expires_at > текущее серверное время
```

Все времена устанавливает сервер, хранит в UTC и возвращает в однозначном формате. Часы клиента не определяют действительность захвата.

`claimed_at` остаётся временем начала текущего захвата. `renew` меняет `lease_expires_at`, но не `claimed_at` и не `claim_id`. Длительность lease в MVP составляет 30 минут.

### 8.3. Атомарность

Выбор задачи и установка захвата — одна атомарная серверная операция с проверкой актуального состояния и зависимостей.

Проверка захвата и защищаемая им запись также атомарны. Это относится к продлению, освобождению, завершению, сохранению прогресса, записи и удалению артефактов.

Нельзя разделять проверку и изменение так, чтобы между ними задачу мог получить другой исполнитель.

При конкурентных запросах сервер не выдаёт два действующих захвата одной задачи. Ошибки временной конкуренции БД обрабатываются ограниченно и предсказуемо; бесконечных повторов нет.

### 8.4. Истечение

Истечение lease не запускает фоновый перевод статуса. Задача остаётся `in_progress`, но получает вычисляемое `lease_expired: true` и при выполнении остальных условий может быть захвачена повторно.

После истечения старый владелец не может продлевать, завершать, освобождать задачу или менять её результаты прежним токеном. Для продолжения нужен новый захват.

Повторный захват заменяет поля владельца и выдаёт новый `claim_id`. Существующие артефакты и краткий прогресс сохраняются.

Просроченный lease означает потерю права записи в трекер, а не доказанную остановку процесса агента. MVP не блокирует старому процессу доступ к файлам, Git и внешним сервисам и не гарантирует однократность внешней работы.

### 8.5. Продление

Первый MVP предоставляет явную команду `renew`. CLI не запускает постоянный heartbeat-процесс и не пытается определять здоровье агента.

Длительность lease задаётся единым серверным соглашением и составляет 30 минут. Чтение задачи не продлевает lease автоматически. Рекомендуемая частота продления утверждается при реализации `renew`.

### 8.6. Одна активная задача и восстановление ответа

Предлагаемое ограничение MVP: не более одной задачи с действующим захватом на пару (`project`, `session_id`).

В этом варианте:

- `claim-next` сначала возвращает уже действующую задачу сессии, если она есть;
- повторный `claim` той же задачи этой сессией возвращает существующий захват без неявного продления;
- попытка захватить другую задачу при действующем захвате отклоняется;
- `current` возвращает актуальную действующую задачу и её контекст без изменения lease.

Проверка ограничения должна быть защищена от конкурентных запросов той же сессии.

Это помогает после потери ответа на захват, но не является универсальной идемпотентностью. После истечения, завершения или освобождения ситуация могла измениться. CLI не должен бесконтрольно повторять создающие запросы или обещать выполнение каждой операции ровно один раз.

При неоднозначной сетевой ошибке CLI сообщает, что операция могла выполниться, и предоставляет способ проверить состояние через `current` или просмотр записи. Повторный запрос не должен молча скрывать конфликт версии или заменять новый захват старым.

## 9. Артефакты

### 9.1. Владение и формат

Артефакт принадлежит задаче независимо от сессии и захвата. Смена исполнителя не меняет его принадлежность и не удаляет содержимое.

В первом MVP поддерживается Markdown-текст. Бинарные данные и вложения не принимаются. Пустые результаты заранее не создаются; отсутствие артефакта допустимо.

Сервер не интерпретирует Markdown как код, не исполняет инструкции из него и не читает локальные пути, упомянутые в содержимом.

### 9.2. Запись

Создание, обновление и удаление артефакта требуют действующего захвата задачи. Значение `session_id` без текущего `claim_id` не заменяет проверку владения.

Для обновления клиент передаёт прочитанную версию артефакта. При несовпадении сервер возвращает конфликт и сохраняет более свежую редакцию. Новая запись того же ключа не создаёт дубликат.

Для удаления также требуется проверка ожидаемой версии, чтобы не удалить документ, изменившийся после чтения.

Утверждённый контракт: `lock_version: null` означает создание отсутствующего артефакта; целое значение означает изменение или удаление существующей редакции. Если фактическое состояние не соответствует ожиданию, возвращается `artifact_version_conflict`.

Проверка lease и проверка версии выполняются совместно с записью. Версия защищает документ от запоздавшего обновления; lease — задачу от прежнего владельца. Эти механизмы не заменяют друг друга.

### 9.3. Завершённые результаты

После завершения задачи её артефакты доступны только для чтения. Новое уточнение результата предпочтительно оформлять новой задачей. Исключение возможно только через явно разрешённое безопасное переоткрытие задачи, а не обход проверок через endpoint артефактов.

В MVP нет истории содержимого, автоматических снимков, статусов `draft` / `approved` и проверки соответствия шаблону. `lock_version` не является архивом редакций.

Наличие артефакта не доказывает завершение шага. Оценка качества и полноты относится к исполнителю и будущим инструкциям.

### 9.4. Единственный источник истины

БД является источником истины для артефактов задач. Не поддерживается параллельная редактируемая копия того же артефакта в Git с автоматической синхронизацией. В Brief v1 артефакт — снимок согласованных решений и передачи контекста; опубликованный проектный Markdown-файл — поддерживаемый источник истины о требуемом поведении для дальнейшей работы. Их изменения не синхронизируются автоматически; изменение нормы требует нового явного согласования.

Формат постоянной документации определяется целевым проектом; путь задают его правила, иначе `docs/` для нормативной спецификации Brief и текущего поведения затронутых доменов. Это клиентский сценарий и не меняет контракт хранения KOS, не вводит серверный экспорт или синхронизацию документов.

## 10. Контекст задачи и выбор работы

### 10.1. Состав контекста

Подробный просмотр, `current` и успешный захват возвращают:

- постановку, тип, статус и `work_summary` задачи;
- её артефакты с `key`, содержимым и версией;
- название, тип и описание группы, если она есть;
- непосредственные зависимости: идентификаторы, названия, состояния, краткие итоги и артефакты;
- краткие сведения о задачах, которые блокируются данной задачей;
- вычисляемую доступность и причины недоступности;
- сведения о собственном захвате в ответах операций владельца.

Каждый артефакт из зависимости сохраняет явный источник: задача, ключ и версия. Результаты разных задач не объединяются в документ без указания происхождения.

Обычный просмотр не раскрывает `claim_id` чужого захвата. Метаданные владельца и срок lease могут быть видимы. В локальной модели выдача собственного контекста по `session_id` не считается полноценной системой аутентификации.

### 10.2. Ограничение объёма

Списки проектов, групп и задач возвращают краткие записи, а не все документы. Списки должны иметь ограничение размера и явный механизм продолжения.

В подробный контекст по умолчанию входят непосредственные, а не рекурсивно все зависимости. Если задаче нужен результат далёкого предшественника, связь задаётся явно либо используется дополнительный просмотр.

Нельзя молча обрезать спецификацию или скрывать часть возвращаемого набора. При ограничении размера ответ сообщает о неполноте и способе получить остальное. Не требуется гарантировать один HTTP-ответ для графа произвольного размера.

### 10.3. Выбор

`ready` только показывает доступные задачи. `claim-next` выбирает и захватывает задачу на сервере и сразу возвращает контекст.

Предлагаемый порядок без приоритетов: сначала `created_at`, затем `id`. Фильтрация по типу поддерживается без серверной интерпретации этого типа. Фильтрация по группе может быть обычным условием выборки.

Если применяется ограничение одной активной задачи и текущий захват найден, `claim-next` явно сообщает, что вернул уже начатую работу, а не выбрал новую. Это не скрытый захват второй задачи по другому фильтру.

Если доступной работы нет, это нормальный результат, а не ошибка сервера.

## 11. Предлагаемый REST-контракт

Пути ниже — проект технического контракта. Они не добавляют новых возможностей сверх описанной модели. Префикс `/api/v1` используется как предлагаемое соглашение.

Формат запросов и ответов — JSON. Для scoped-операций параметр `project` содержит канонический ключ репозитория. CLI передаёт контекст проекта и для операций по ID, чтобы сервер мог обнаружить обращение не к тому проекту.

### 11.1. CRUD

| Операции | Ресурс |
| --- | --- |
| GET, POST | `/api/v1/projects` |
| GET, PATCH, DELETE | `/api/v1/projects/:id` |
| GET, POST | `/api/v1/task-groups` |
| GET, PATCH, DELETE | `/api/v1/task-groups/:id` |
| GET, POST | `/api/v1/tasks` |
| GET, PATCH, DELETE | `/api/v1/tasks/:id` |
| GET, POST | `/api/v1/workflows` (список включает общие определения; POST с `global: true` без `project` создаёт общее) |
| GET, DELETE | `/api/v1/workflows/:id` |

При создании и разрешённом обновлении задачи `blocked_by_ids` задаёт полный желаемый набор непосредственных блокеров. Отсутствие поля в PATCH не меняет зависимости; пустой массив явно очищает их. Проверка и изменение набора атомарны.

Пример создания задачи:

```json
{
  "project": "github.com/owner/project",
  "workflow_id": 1,
  "task_group_id": 3,
  "kind": "feature",
  "title": "Добавить восстановление пароля",
  "description": "Цель, ограничения и ожидаемый результат.",
  "blocked_by_ids": [10, 11]
}
```

### 11.2. Работа с задачей

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/v1/tasks/ready` | Доступные задачи без захвата |
| GET | `/api/v1/tasks/current` | Действующая задача сессии с контекстом |
| POST | `/api/v1/tasks/claim-next` | Выбор, захват и контекст |
| POST | `/api/v1/tasks/:id/claim` | Захват определённой задачи |
| POST | `/api/v1/tasks/:id/renew` | Продление lease |
| POST | `/api/v1/tasks/:id/release` | Освобождение задачи |
| POST | `/api/v1/tasks/:id/complete` | Завершение задачи |
| POST | `/api/v1/tasks/:id/reopen` | Безопасное явное переоткрытие |
| GET | `/api/v1/tasks/:id/step` | Инструкция, входы и выходы текущего шага |
| POST | `/api/v1/tasks/:id/advance` | Переход к следующему шагу по действующему claim и `expected_step` |

Захват принимает `session_id`. Защищённые операции принимают `claim_id`; поля владельца из тела запроса не присваиваются модели напрямую.

`release` и `complete` могут принимать новый `work_summary`, чтобы сохранить итог и изменить состояние одной операцией.

`claim`, `claim-next` и `current` с `context: "route"` возвращают короткий маршрут без документов; без параметра сохраняется подробный контекст. `advance` сравнивает `expected_step` с текущим под блокировкой; несоответствие даёт `step_conflict` (409). На последнем шаге продвижение недопустимо, а `complete` допустимо только на нём. Это не оценка качества результата.

Для клиентской интеграции OpenCode CLI поддерживает явный вывод маршрута с `claim_fingerprint` вместо полного `claim_id`. Отпечаток — SHA-256 случайного серверного токена, а не новый серверный credential. В режиме защищённой записи по отпечатку CLI считывает `current` по устойчивой сессии, проверяет ID задачи, отпечаток и для записи выхода ожидаемую позицию шага; затем отправляет полученный токен и `expected_step` в API записи артефакта. Сервер в одной транзакции проверяет claim и переданную позицию шага; смена захвата или шага между чтением и записью даёт конфликт. При несовпадении текущей позиции/отпечатка CLI прекращает операцию до отправки записи и возвращает машиночитаемый конфликт. Старые REST-запросы без `expected_step` и режим явного `--claim` сохраняются. Полный `claim_id` фильтруется из журналов запросов Rails.

Список артефактов задачи возвращается страницами по возрастанию ID: по умолчанию 50 записей, не более 100 за запрос. Ответ содержит `pagination.limit` и `pagination.next_after_id`; CLI принимает `--limit` и `--after-id` для продолжения. Контент каждого артефакта возвращается целиком, как и прежде.

Пример отсутствия работы:

```json
{
  "data": {
    "task": null,
    "reason": "no_ready_tasks"
  }
}
```

Для `current` без действующей задачи используется отдельная причина `no_current_task`.

### 11.3. Артефакты

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/api/v1/tasks/:id/artifacts` | Артефакты задачи |
| GET | `/api/v1/tasks/:id/artifacts/:key` | Один артефакт |
| PUT | `/api/v1/tasks/:id/artifacts/:key` | Создание или замена ожидаемой редакции |
| DELETE | `/api/v1/tasks/:id/artifacts/:key` | Удаление ожидаемой редакции |

Пример обновления:

```json
{
  "project": "github.com/owner/project",
  "claim_id": "server-issued-claim-id",
  "lock_version": 2,
  "content": "# Спецификация\n\nЗаполненное содержимое документа."
}
```

Успешная запись возвращает артефакт с актуальной версией. Переименование ключа отдельной операцией в MVP не требуется.

### 11.4. Ответы и ошибки

Успех возвращается в объекте `data`. Ошибка имеет машиночитаемый код, сообщение и при необходимости подробности:

```json
{
  "error": {
    "code": "lease_expired",
    "message": "Срок действия захвата истёк.",
    "details": {
      "task_id": 42
    }
  }
}
```

Предлагаемые категории: 400 для некорректного запроса, 404 для отсутствующей записи, 409 для конфликта состояния или версии, 422 для нарушений правил данных. Временная недоступность сервера или БД отличается от бизнес-конфликта.

Коды должны позволять различать как минимум:

- `not_found`
- `validation_failed`
- `task_blocked`
- `task_already_claimed`
- `session_has_active_task`
- `claim_mismatch`
- `lease_expired`
- `artifact_version_conflict`
- `dependency_cycle`
- `invalid_transition`
- `database_busy`

Конфликт не должен частично сохранять изменения. Повторное завершение уже завершённой задачи не объявляется автоматически успешно выполненным тем же захватом, если сервер не может это доказать; клиент проверяет текущее состояние.

## 12. Предлагаемый CLI-контракт

В примерах используется условное имя `agt`. Это не утверждённое название проекта или гема.

### 12.1. Общие соглашения

- JSON в stdout по умолчанию; диагностика в stderr.
- Стабильные ненулевые коды завершения при ошибках.
- Отсутствие интерактивных вопросов и обязательного открытия редактора.
- Ввод длинных описаний и артефактов из UTF-8-файла или stdin.
- Конечные тайм-ауты HTTP; ошибки соединения отличаются от отказов API.
- Не логировать полные токены захватов и не печатать их в диагностике.
- Аргументы командной строки имеют приоритет перед переменными окружения.
- Не нужен обязательный проектный конфигурационный файл.

Предлагаемые параметры:

| Параметр | Назначение |
| --- | --- |
| `--url` | Адрес сервера; по умолчанию локальный |
| `--project` | Явный канонический ключ проекта вместо Git-определения |
| `--session` | Идентификатор сессии |
| `--claim` | Идентификатор действующего захвата |

Имена переменных окружения выбираются вместе с окончательным названием CLI. Сессия и захват могут передаваться окружением; CLI не хранит один общий «текущий захват» в файле репозитория, который разделяют разные агенты.

### 12.2. Команды

```text
agt project create|list|show|update|delete
agt session new
agt group create|list|show|update|delete
agt task create|list|show|update|delete

agt task ready
agt task claim-next
agt task claim ID
agt task current
agt task renew ID
agt task release ID
agt task complete ID
agt task reopen ID
agt workflow create --file PATH
agt workflow list|show|delete
agt task step show ID
agt task advance ID --expected-step N

agt task artifact list TASK_ID
agt task artifact get TASK_ID KEY
agt task artifact put TASK_ID KEY --file PATH
agt task artifact delete TASK_ID KEY
```

Команды создания и обновления задачи поддерживают группу и `blocked_by_ids` в одном запросе. Отдельные команды добавления и удаления одной зависимости допустимы как удобство, но не обязательны для первого MVP.

В утверждённом CLI `kos session new` возвращает `data.session_id` (случайный непрозрачный ID), не требует Git-проекта, сети или существующего сервера и не хранит ID. Вызовы независимы; агент повторно использует один полученный ID в пределах своей беседы.

`artifact put` из stdin должен быть возможен без временного файла. Для обновления и удаления передаётся ожидаемая версия.

`task show`, `task current` и результат захвата возвращают подробный контекст по общему серверному контракту. CLI не выполняет несколько скрытых запросов, когда сервер уже умеет вернуть требуемый набор за один.

### 12.3. Неоднозначные результаты

Отсутствие доступной задачи — успешный результат с `task: null`, а не ненулевой exit code.

Если соединение оборвалось после отправки изменяющего запроса, CLI не утверждает, что операция не выполнилась. Он возвращает различимую ошибку неопределённого результата и указывает подходящую команду проверки состояния.

Не реализовывать общую автоматическую повторную отправку всех POST-запросов. Постоянный журнал идемпотентности запросов пока не обязателен.

## 13. Хранение, конкурентность и надёжность

### 13.1. Транзакции и инварианты

Короткими атомарными операциями должны быть как минимум:

- создание задачи вместе с зависимостями;
- проверка и изменение графа зависимостей;
- выбор и захват с проверкой ограничений сессии;
- проверка lease и обновление задачи или артефакта;
- защищённые операции удаления и переоткрытия.

Нельзя предполагать, что отдельная проверка Rails-валидацией автоматически защищает от конкурентного запроса. Корректность должна подтверждаться тестами на фактической SQLite-конфигурации проекта.

Внутри транзакции нет обращений к AI, Git, HTTP-сервисам или других длительных операций. Пользовательские документы не передаются в SQL как исполняемый текст.

### 13.2. Локальная эксплуатация

Перезапуск приложения не теряет задачи, артефакты и сведения о lease. Сроки остаются корректными после перезапуска и не вычисляются из времени жизни процесса.

README описывает запуск, миграции, расположение данных, проверенный способ резервного копирования и восстановление локальной БД. Отдельный сервис бэкапов в MVP не создаётся.

### 13.3. Границы гарантий

Сервер гарантирует корректность собственных данных и отклонение записей устаревшего владельца. Он не гарантирует:

- что агент действительно продолжает работать;
- что выполнены тесты, ревью и другие инструкции;
- что артефакт качественный и полный;
- что изменение интегрировано в `main`;
- что старый агент перестал менять файлы;
- что неоднозначно завершившийся сетевой запрос безопасно повторять без проверки.

Такие ограничения должны быть явно отражены в README и поведении CLI, а не скрываться за статусом `done`.

```text
  README.md
```

Точные имена модулей и исполняемого файла выбираются отдельно. CLI устанавливается как Ruby-гем и не зависит от загрузки Rails-приложения или его моделей. Общая библиотека бизнес-логики между CLI и сервером не нужна: правила находятся на сервере.

Документированный минимальный путь установки CLI — получить исходники из GitHub-репозитория, собрать `.gem` и установить его. Установка должна быть проверена с чистого окружения. Публикация на RubyGems и отдельная система обновлений не обязательны.

Используемые версии Ruby, Rails и зависимостей фиксируются в проекте при старте реализации. Эта спецификация не требует выбора новейших версий и не привязывает реализацию к конкретным ещё не проверенным версиям.

Skills OpenCode создаются отдельно для текущего сценария маршрута и контекста шага (PLAN-014); не создавать генераторы шаблонов или Git-автоматизацию только ради будущей структуры каталогов.

## 15. Сценарии приёмки

MVP считается работающим после проверки следующих сценариев.

### 15.1. Основной цикл

Из Git-репозитория через CLI создаётся workflow и задача с его ID, проект определяется без отдельной настройки. Другая команда находит доступную работу, захватывает её одним запросом и получает контекст. Исполнитель сохраняет артефакт и завершает задачу. Задача больше не выдаётся как доступная.

### 15.2. Независимые клоны

Два каталога с эквивалентным SSH/HTTPS remote обращаются к одному проекту. Отсутствие Git или remote даёт понятную ошибку; явный проект позволяет работать вне репозитория.

### 15.3. Группа и планирование

Создаётся группа `epic` и задача декомпозиции. Пока она выполняется, созданные с зависимостью задачи недоступны. После её завершения они могут быть захвачены. Контекст содержит артефакты планирования. После завершения всех задач группа вычисляется как завершённая.

### 15.4. Конкурентный захват

Два запроса разных сессий одновременно претендуют на одну задачу. Только один получает действующий захват; второй получает другой доступный результат, отсутствие работы или соответствующий конфликт в зависимости от операции.

При принятии ограничения одной задачи на сессию два параллельных запроса одной сессии не захватывают две разные задачи одного проекта.

### 15.5. Истечение и прежний владелец

После истечения lease задача остаётся `in_progress`, но доступна для повторного захвата. Новый захват имеет другой `claim_id`. Старые `renew`, `release`, `complete`, сохранение прогресса и запись артефакта отклоняются. Данные нового владельца не повреждаются.

### 15.6. Продление

Действующий владелец продлевает срок без смены `claimed_at` и `claim_id`. Чтение не продлевает захват. В момент `lease_expires_at <= now` прежний токен уже недействителен.

### 15.7. Восстановление контекста

После перезапуска CLI или смены исполнителя ранее созданные артефакты и `work_summary` доступны. Получение контекста не создаёт новую задачу и не стирает результаты.

### 15.8. Конфликт документа

Два обновления используют одну прочитанную версию артефакта. Первое сохраняется, второе получает конфликт. Более свежий текст остаётся в БД. Конкурентное создание одинакового (`task_id`, `key`) не создаёт дубликат.

### 15.9. Корректность графа

Отклоняются самозависимость, цикл, дубликат связи и зависимость между проектами. В том числе проверяется конкурентное добавление отношений, которые вместе образовали бы цикл.

Ошибка создания одной из зависимостей не оставляет частично созданную задачу без нужных блокировок.

### 15.10. Защита переходов

Изменение `status`, владельца и срока lease через обычный PATCH не позволяет обойти операции состояния. Запись артефакта без действующего захвата отклоняется. Изменение и удаление блокеров не нарушает уже выполняющуюся зависимую работу.

### 15.11. Сеть и ошибки

Потеря ответа не приводит к бесконтрольному созданию новых задач или захватов клиентом. CLI различает отсутствие работы, бизнес-конфликт, конфликт версии и ошибку соединения. Машиночитаемый вывод остаётся валидным JSON.

### 15.12. Границы продукта

Ни одна штатная команда Rails API или CLI KOS не создаёт worktree, не меняет ветки, не коммитит, не делает push/merge и не вызывает GitHub API. Клиентская интеграция OpenCode может выполнять явно описанные Git-операции по правилам проекта (PLAN-019/020). Сервер не требует OpenCode, Redis или установленных skills; определения workflow создаются через API/CLI.

### 15.13. Маршрут и исполнение шага

Создаётся workflow из двух шагов: первый `subagent` с уровнем `standard` или `advanced`, второй `main`. Задача привязывается к workflow своего проекта или общему определению. Компактный захват показывает маршрут первого шага без артефактов, запрос пакета возвращает инструкцию и явно отмеченный отсутствующий вход. После сохранения результата под действующим claim оркестратор продвигает задачу с ожидаемой позицией; повторный запрос возвращает конфликт. На втором шаге пакет содержит результат первого, затем задача завершается. Просроченный claim не продвигает шаг; повторный захват сохраняет указатель и документы. Конкурентные запросы не пропускают шаг. Workflow другого проекта не принимается; используемое определение не редактируется и не удаляется.

## 16. Реализация небольшими инкрементами

Последовательность — рекомендация по разработке, а не отдельный механизм workflow продукта.

1. Вертикальный CRUD. Локальный Rails, SQLite, проекты, задачи и минимальный CLI; установка гема и базовый JSON-контракт.
2. Группы и зависимости. `TaskGroup`, вычисляемая готовность, атомарное создание связей, проверка циклов и список доступной работы.
3. Безопасное выполнение. Сессии, `claim`, `claim-next`, lease, `current`, продление, освобождение, завершение и конкурентные тесты.
4. Артефакты и полный контекст. Хранение Markdown, проверка версии и владельца, результаты зависимостей, ввод через файл/stdin, сквозные сценарии.

Каждый инкремент должен быть работоспособным и проверяемым. Не начинать со сложных универсальных абстракций, плагинной системы или набора таблиц для ещё не реализуемых шагов.

## 17. Технические соглашения

Соглашения, утверждённые 28 сентября 2026 года для первого вертикального среза:

- проект называется `KOS`, Rails-модуль — `Kos`, CLI-гем — `kos-cli`, исполняемая команда — `kos`;
- используются Ruby 3.4.10 и Rails 8.1.3.1;
- API использует prefix `/api/v1`; изначальный локальный URL `http://127.0.0.1:3000` заменён на `http://127.0.0.1:3137` в PLAN-031;
- списки используют `limit=50` по умолчанию, максимум 100 и продолжение через `after_id`;
- успешные ответы используют обёртку `data`, ошибки — обёртку `error`;
- автосоздание проекта не входит в CRUD проектов и применяется при создании проектных workflow, групп и задач с общим workflow; задачам требуется своё проектное либо общее определение workflow.

Соглашения, утверждённые 29 сентября 2026 года для полного контекста задачи:

- `task show`, `current`, `claim` и `claim-next` используют общий подробный объект задачи; `claim_id` присутствует только в ответах владельца;
- собственные артефакты, непосредственные блокеры, артефакты блокеров и зависимые задачи ограничиваются независимо через `context_limit=50` (максимум 100);
- продолжение этих наборов использует соответственно `artifact_after_id`, `blocked_by_after_id`, `dependency_artifact_after_id` и `blocks_after_id`; метаданные каждого набора явно сообщают полноту и следующий курсор;
- артефакт блокера содержит явный источник с идентификатором задачи, ключом и версией.

Соглашения, утверждённые 29 сентября 2026 года для надёжности CLI:

- JSON успеха и ошибки пишется в stdout, а отдельная диагностика — в stderr;
- exit codes: `0` — успех, `1` — ошибка API, `2` — некорректный вызов или определение проекта, `3` — ошибка соединения, `4` — конфликт API, `5` — неопределённый результат изменяющего запроса;
- переменные окружения называются `KOS_API_URL`, `KOS_PROJECT`, `KOS_SESSION_ID` и `KOS_CLAIM_ID`; одноимённые CLI-параметры имеют приоритет;
- для OpenCode клиентский `--fingerprint` на `claim`/`claim-next`/`current` заменяет вывод `claim_id` на SHA-256 `claim_fingerprint` и включает компактный маршрут; глобальный `--claim-fingerprint HASH` использует `--session`/`KOS_SESSION_ID` для считывания действующего claim внутри CLI при защищённой операции; запись артефакта в этом режиме требует `--expected-step N`;
- connection timeout составляет 5 секунд, read и write timeout — по 15 секунд;
- обрыв изменяющего запроса после установки соединения и некорректный ответ на него возвращают `ambiguous_result` без автоматического повтора и с командой проверки состояния.

Остальные строки таблицы пока остаются предложениями и утверждаются до реализации соответствующего поведения.

Соглашения о расширении MVP утверждены 29 сентября 2026 года: workflow хранится на сервере и обязательно для каждой новой задачи; текущий шаг хранится в задаче, маршрут доступен компактно, а инструкцию и входы исполнитель запрашивает отдельно. Шаг задаёт `main`/`subagent` и только для субагента один из уровней `standard`/`advanced`. Захват принадлежит задаче, продвижение выполняется явно. Для OpenCode первоначальная передача полного claim субагенту заменена согласованной в PLAN-016 передачей отпечатка и внутренним получением токена CLI по сессии перед записью; сервер по-прежнему проверяет исходный claim. Workflow управляются через API/CLI и не меняются после создания. Обратная совместимость старых задач не требуется; они очищаются при миграции. Для отдельного клиентского пакета OpenCode PLAN-014 согласованы глобальная установка skills из исходников KOS и сопоставление `standard` = `openai/gpt-6-luna`, `advanced` = `openai/gpt-6-sol`. Модель основного агента задаётся в OpenCode; шаг `main` выполняет он сам. Контракт Rails не меняется; CLI получил явный opt-in режим отпечатка.

## 18. Будущее развитие — не реализовывать сейчас

### 18.1. Дальнейшее развитие workflow

В дальнейшем возможно расширить определение workflow:

- шаблоны этих артефактов.

Шаблон принадлежит схеме, заполненный результат — конкретной задаче. Артефакт `specification` является одним из результатов, а не специальным исключением модели.

Изменения используемых определений сейчас создаются новой записью; в будущем можно проектировать версии шаблонов и расширенные критерии завершения, не переписывая созданные документы и не меняя правила посреди выполнения.

### 18.2. Git-workflow

Для задач разработки в клиентской интеграции OpenCode работа выполняется в отдельном worktree задачи. Ранее предполагалось вливание ветки в `main`; актуальное правило PLAN-020: назначение и способ публикации определяются правилами целевого проекта. При отсутствии правил публикации агент уточняет их, а не выбирает `main` автоматически.

Это не универсальное условие для всех задач: результат декомпозиции может находиться только в трекере. Признак разработки задаётся явной постановкой или правилами проекта, а не значением `kind` сам по себе.

В текущем MVP команда `complete` доверяет заявлению исполнителя и не проверяет репозиторий.

### 18.3. Другие группы

Возможны инициативы и другие типы группировки. Для них отдельно определяется необходимость вложенности, членства в нескольких группах и иной семантики готовности.

Наличие поля `kind` сейчас не означает, что все эти отношения уже поддерживаются.

### 18.4. Skills и документация

OpenCode — первый клиент интеграции PLAN-014, но серверный контракт остаётся универсальным. Клиентская публикация нормативной спецификации Brief v1 следует правилам проекта; серверный экспорт, синхронизация документов и универсальный стандарт документации разных проектов остаются вне MVP.

## Итог

Первый продукт — локальный трекер, а не оркестратор выполнения.

Проекты определяются репозиториями. Группы объединяют задачи. Зависимости определяют доступность и входные результаты. Захваты защищают изменения от устаревшего исполнителя. Артефакты хранят результаты задач. Rails обеспечивает правила, Ruby CLI предоставляет доступ.
