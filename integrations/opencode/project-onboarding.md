# Connect a target project to KOS

Use this procedure when installing KOS for a **selected** project, or when the human asks to start a new project and Brief from an empty directory or without a directory. Installing global OpenCode skills alone does not select or modify any target repository. KOS identifies a project by its Git repository key, not by its directory name or display name.

1. Discuss the project's purpose and expected outcome, preferred directory, repository host/owner/name, whether a remote repository already exists, who should create it and where the normative specification will be published. Ask only for missing consequential decisions; do not pick an account, remote URL or publication destination on the human's behalf. Speak the human's language or the language required by existing project instructions. Number answer choices `1.`, `2.`, ... and request a reply with one digit. This preliminary conversation may occur in Plan without writing files or KOS records. Continue in Build only after the necessary choices are agreed.
2. Inspect the proposed path, any existing files, Git status, `origin` and applicable project rules before acting. If no directory exists, create only the agreed directory; if it is empty and has no repository, initialize Git according to the agreed project rules. An existing checkout is reused without overwriting its files or history. For an existing remote, verify its identity and access. If the remote must be created, agree **in this project's conversation** whether the agent or human creates it and follow that choice; do not assume GitHub or create a remote account automatically. Configure or verify a real `origin` that identifies the agreed repository; a made-up or merely planned URL is insufficient. If `origin` conflicts, a path is occupied, or access/publication cannot be verified, investigate and ask for the specific human action needed. Do not register an unrelated KOS project or duplicate a repository while recovering from partial setup.
3. In the **selected project's root** create or conservatively extend `AGENTS.md` with a short `## KOS task tracking` section. Preserve existing rules, language and formatting; if the section already expresses the same guidance, leave it alone. If it conflicts, ask for a resolution before changing it. Include: this project tracks work in KOS; on an actual task request load `kos-orchestrator` (or use `/kos`), identify this repository by its verified `origin`, generate a conversation ID with `kos session new` only if none exists, follow the project's own development/publication rules, and use the person's language or the explicit language rule in this file. Do not add credentials, claim IDs or machine-specific paths. Review the diff. This file is project setup, agreed separately from approval of Brief requirements. Follow its publication rules rather than modifying unrelated projects during global KOS installation. An empty Git repository has no base commit for a task worktree: create and publish a minimal initial commit under the agreed project publication rules, verify the destination, and then prepare the Brief worktree. If publication cannot be verified, ask for the missing human action before claiming Brief; do not mistake `git init` or adding `origin` for a publishable base.
4. Before creating a Brief, verify `origin` resolves to the intended canonical key, the local KOS CLI/server are available, and `kos --project KEY workflow list` includes shared `KOS Brief v1` (verify the response and ID; do not guess an ID). On retry, inspect the existing project and tasks; a not-found task list before first registration is expected, not a signal to register a second project. If there is no existing Brief for this request, create one with `kos --project KEY task create --workflow-id ID --kind decomposition --title ... --description ...` in Build. Task creation registers the KOS project atomically when needed. Use the established conversation ID and follow `kos-orchestrator` to claim and perform the Brief. For a new Brief, high-level decisions and acceptance criteria still require explicit human agreement before artifacts, dependent tasks or project specification edits. Publication of the approved specification must be possible before Brief can be completed.
5. On an ambiguous write or setup failure, inspect actual files, Git origin, KOS project/task state and publication destination before retrying. Never interpret an external command's exit status alone as proof of publication. If remote access or publication needs a human action, state exactly what is needed and leave the task at its current step; do not mark it done. A second run reuses verified directory, AGENTS.md guidance, repository and existing KOS records instead of creating duplicates.
