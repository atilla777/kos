# Connect a target project to KOS

Use this procedure when installing KOS for a **selected** project, or when the human asks to start a new project and Brief from an empty directory or without a directory. Installing global OpenCode skills alone does not select or modify any target repository. KOS identifies a project by its Git repository key, not by its directory name or display name.

## Short route

1. Agree on the purpose, directory, host, owner/account and repository name, who creates a missing remote, the project's publication rules and destination, access boundary (local/trusted or external), and OKF bundle location (`docs/` by default). Ask only missing consequential questions, one at a time in ordinary chat; never invent an account or destination. Discussion may happen in read-only Plan.
2. Inspect existing files, rules, Git status and actual `origin`. Check the account identity and repository access **on the selected host** using its available tools; do not require GitHub for other hosts. Verify that `origin` identifies the intended repository and that the agreed destination is reachable. Reuse a verified existing checkout and base; do not create a second repository or commit on repeat entry.
3. For missing setup, obtain explicit agreement to prepare the repository; obtain a **separate** agreement to make and publish the initial commit, and later separate Brief approval. In Build, prepare only the agreed directory and real remote, add KOS guidance to the selected project's `AGENTS.md`, then create and publish a minimal base commit by the project's rules. Verify the base at its destination before preparing a Brief worktree or claiming Brief. If access or publication is unclear, stop and resolve it; `git init`, an `origin` URL and a successful command exit alone are not publication evidence.
4. Check the canonical key, CLI/server and verified ID of shared `KOS Brief v5`. Reconcile existing tasks before creating a new Brief. Then discuss requirements and plan, obtain their **separate explicit approvals**, and proceed with the Brief workflow; repository consent and switching mode never imply Brief approval. Confirm publication of the approved specification before completing Brief.

## Details and recovery

Use the person's language or that required by the target project's `AGENTS.md`; explain decisions plainly. Number choice options and request one digit, recommend with a short reason in parentheses; for unknown facts recommend how to establish them. Never select an account, URL or publication destination for the human. Inspect the proposed path before creating it; if empty, initialize Git only under agreed project rules. For a remote that must be created, agree in this project's conversation whether the person or agent creates it. Check the chosen host identity, remote access and destination without displaying credentials or tokens embedded in Git URLs. A proposed URL is not a real `origin`; conflicts, occupied paths or unavailable access require clarification before writing. Preserve existing files and history.

In the selected project's root, create or conservatively extend `AGENTS.md` with a short `## KOS task tracking` section; leave an equivalent section alone and resolve conflicts before editing. Include how to load `kos-orchestrator` on an actual task request, identify the verified `origin`, generate a conversation ID only if none exists, follow the project's development/publication rules and use the person's language or the file's language rule. State the one-question-at-a-time rule (sequential wizard allowed), context and reasoned recommendation in parentheses, and plain reports. State that approved required behavior lives in domain-organized OKF v0.2 concepts inside the selected bundle under `docs/`, including externally prepared specifications; material changes need explicit human agreement, while code/tests show actual behavior. Do not include credentials, claims or local machine paths. Review the diff. An empty Git repository cannot support the Brief task worktree until the initial commit is published and confirmed at the project-defined destination.

Before creating Brief, verify `origin` resolves to the intended canonical key, the local KOS CLI/server are available, and `kos --project KEY workflow list` includes shared `KOS Brief v5` with its actual ID; never guess or silently fall back. On retry, inspect existing project/tasks (a not-found list before registration is normal). If no matching Brief exists, in Build use `kos --project KEY task create --workflow-id ID --kind decomposition --title ... --description ...`; creation registers the project atomically. Use the established conversation ID and follow `kos-orchestrator`. Before Brief artifacts, dependent tasks or normative project edits, explicitly approve its required behavior and high-level plan separately. The approved specification must have a verified publication route.

On failure or ambiguous write, inspect actual files, Git origin, KOS project/task state and publication destination before retrying. Never infer publication from an exit status. State the exact human action needed when access or publication is blocked and leave the task at its actual step. On return reuse verified directory, guidance, repository and KOS records; never create duplicates.
