# Connect a target project to KOS

Use this procedure when installing KOS for a **selected** project, or when the human asks to start a new project and Brief from an empty directory or without a directory. Installing global OpenCode skills alone does not select or modify any target repository. KOS identifies a project by its Git repository key, not by its directory name or display name.

## Short route

1. Agree on the purpose, directory, host, owner/account and repository name, who creates a missing remote, the project's publication rules and destination, access boundary (local/trusted or external), and OKF bundle location (`docs/` by default). Ask only missing consequential questions, one at a time in ordinary chat; never invent an account or destination. Discussion may happen in read-only Plan.
2. Inspect existing files, rules, Git status and actual `origin`. Check the account identity and repository access **on the selected host** using its available tools; do not require GitHub for other hosts. Verify that `origin` identifies the intended repository and that the agreed destination is reachable. Reuse a verified existing checkout and base; do not create a second repository or commit on repeat entry.
3. For missing setup, obtain explicit agreement to prepare the repository; obtain a **separate** agreement to make and publish the initial commit, and later separate Brief approval. In Build, prepare only the agreed directory and real remote, create or conservatively extend the selected project's `AGENTS.md` and required `rules/index.md` using the templates below, then create and publish a minimal base commit by the project's rules. Verify the base at its destination before preparing a Brief worktree or claiming Brief. If access or publication is unclear, stop and resolve it; `git init`, an `origin` URL and a successful command exit alone are not publication evidence.
4. Check the canonical key, CLI/server and shared `KOS Base Brief v1`. Run `kos --project KEY workflow install-base` for the selected project, then verify the ID of its project `KOS Brief v1`. Reconcile existing tasks before creating a new Brief. Then discuss requirements and plan, obtain their **separate explicit approvals**, and proceed with the Brief workflow; repository consent and switching mode never imply Brief approval. Confirm publication of the approved specification before completing Brief.

## Details and recovery

Use the person's language or that required by the target project's `AGENTS.md`; explain decisions plainly. Number choice options and request one digit, recommend with a short reason in parentheses; for unknown facts recommend how to establish them. Never select an account, URL or publication destination for the human. Inspect the proposed path before creating it; if empty, initialize Git only under agreed project rules. For a remote that must be created, agree in this project's conversation whether the person or agent creates it. Check the chosen host identity, remote access and destination without displaying credentials or tokens embedded in Git URLs. A proposed URL is not a real `origin`; conflicts, occupied paths or unavailable access require clarification before writing. Preserve existing files and history.

Use the co-installed `references/AGENTS.template.md` as the source for a new root `AGENTS.md` and as a checklist for an existing one. Replace `{{SPEC_BUNDLE_INDEX}}` with the actual project-selected bundle index (`docs/index.md` by default), never leave a placeholder. For an existing file, keep its text and headings, append or minimally update the KOS section and the link to `rules/index.md` only where missing; leave equivalent guidance alone. Do not overwrite a project rule or assume that agreement to connect the project approves replacing it. Ask the human to resolve contradictory requirements before editing. Do not include credentials, claims or local machine paths.

The selected project's `rules/index.md` is mandatory even before project-specific rules have been agreed. Inspect `rules/`, its index, any existing architecture/style/testing/security/publication rules and root `AGENTS.md` first. If the index is absent, use `references/rules-index.template.md` for a minimal OKF v0.2 index, retaining navigation to existing rule documents and linking the existing `AGENTS.md` as the source for rules still kept there. An existing index may already be part of a bundle: retain its content and add only missing navigation; do not insert a second `okf_version` or duplicate an existing link. If existing `rules/` Markdown is not OKF-compliant, preserve it and agree on how to bring it into the bundle rather than silently converting or discarding it. Do not manufacture architecture or style policies from template headings. Existing rules stay in `AGENTS.md`; moving them into `rules/` requires separate human agreement. New rule concepts in `rules/` use OKF frontmatter with a nonempty `type`, and the index links them. On repeat entry compare both files with the templates and existing rules, fill only missing guidance, and review the diff; if links, paths or policies conflict, ask before editing. This is project onboarding, not the global `script/install-opencode` update, which must not modify arbitrary projects. An empty Git repository cannot support the Brief task worktree until the initial commit is published and confirmed at the project-defined destination.

Before creating Brief, verify `origin` resolves to the intended canonical key and the local CLI/server are available. Check that the three shared bases v1 are installed; otherwise report the missing installation. For this selected project in Build run `kos --project KEY workflow install-base` and inspect `workflow list --brief` and `workflow show ID` for the project `KOS Brief v1`; on retry this returns the same copies. If the project has a later Brief edition, inspect and choose its verified ID instead of falling back to the base or guessing from list order. If no matching Brief task exists, use `kos --project KEY task create --workflow-id ID --kind decomposition --title ... --description ...`. Use the established conversation ID and follow `kos-orchestrator`. Before Brief artifacts, dependent tasks or normative project edits, explicitly approve its required behavior and high-level plan separately. The approved specification must have a verified publication route.

On failure or ambiguous write, inspect actual files, Git origin, KOS project/task state and publication destination before retrying. Never infer publication from an exit status. State the exact human action needed when access or publication is blocked and leave the task at its actual step. On return reuse verified directory, guidance, repository and KOS records; never create duplicates.
