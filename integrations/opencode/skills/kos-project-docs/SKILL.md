# Document the target project's behavior

This skill is invoked explicitly by a Brief specification step or a current-behavior documentation step, not automatically for every KOS task. Work in the verified target project worktree when one is required for publication, otherwise in the target checkout. Follow `kos-executor` for delegated step packets, claim-protected KOS artifacts and reporting; this skill concerns the project's own documents. A task artifact is not a substitute for a maintained project document.

1. Read applicable project instructions (such as `AGENTS.md`) and identify the assigned step. For **current-behavior documentation**, maintain Markdown documentation for each domain affected by user-visible change, even when project rules are silent. Use the project's required path and conventions if specified; otherwise default to `docs/` in the target repository. For an **approved Brief specification**, a maintained normative Markdown file is required: use the project's specification path and conventions where provided, otherwise default to `docs/`. If project rules explicitly forbid documentation or publication, conflict, or leave the destination ambiguous, ask the orchestrator/user rather than overriding them. Do not assume KOS's `docs/knowledge/` applies to other projects.
2. For Brief, inspect existing normative specifications and project navigation before creating a file. Write or update the correct approved requirement for this Brief, with the required behavior, significant normal, alternative, error and edge scenarios, boundaries, testable criteria and decisions with rationale. When valuable use project/task-qualified REQ, AC, DEC and Q references; link the task and related documents. The specification is the source of truth for **what should be**, regardless of implementation progress. Do not insert a manually maintained implementation-status table or portray approval as implementation. KOS tasks and results describe progress. If a later change conflicts with the approved norm, seek an explicit decision rather than silently changing the file. On resumption, inspect existing work to avoid duplicate files.
3. For a current-behavior step, inspect existing documents, task result, tests and actual behavior in each affected domain. Update the appropriate concept or create a distinct one only when needed, keeping project navigation current. Describe the system from a user's point of view: normal, alternative and error scenarios, observable outcomes and limits; reference applicable normative criteria when helpful. Distinguish implemented behavior from required behavior; do not claim tests, verification or release that did not occur. For a task without user-facing change, inspect the affected concepts and report why no update is needed.
4. Use the documentation format required by the project. If it requires [OKF v0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md), write UTF-8 Markdown with appropriate frontmatter and a nonempty `type`, distinguishing a normative specification from a User Feature describing implemented behavior. Follow the project's bundle/index conventions; only a bundle-root index may have `okf_version` frontmatter. Do not assign `verified: human:...` without actual human verification. Otherwise follow the project's existing Markdown format. Preserve unrelated content and metadata.
5. Check links, frontmatter when applicable, alignment with the approved requirements (for Brief) or actual behavior (for current documentation), and applicable project checks. Review the diff and report edits, verification and unresolved questions to the orchestrator. The Brief's publication step publishes and verifies the normative file **before** completing Brief; delegated documentation steps leave publication and advancement to the main agent.
