# Maintain the target project's required behavior

Use this skill when a KOS step explicitly requests it, or when a person requests specification work outside KOS. Work in the verified target checkout or task worktree. Follow `kos-executor` for delegated step packets and claim-protected artifacts; this skill concerns the project's own maintained documents. KOS artifacts are snapshots and progress reports, not the source of truth for required behavior.

When discussing KOS specification decisions with a person, follow the same dialogue rules as `kos-orchestrator`: explain context plainly without unnecessary jargon or loanwords, ask one question at a time in ordinary chat (or use a wizard that shows questions sequentially), and give a recommendation with a short reason in parentheses without inventing facts. Keep progress and final reports understandable too. Obtain separate explicit approval for changed required behavior.

1. Read `AGENTS.md`, the mandatory `rules/index.md` and applicable OKF v0.2 rule concepts, then locate the user-facing OKF v0.2 bundle inside `docs/`. Default to `docs/` itself; a project may specify a subdirectory such as `docs/knowledge/`. Preserve existing compatible documents and navigation rather than creating duplicates. Other technical files in `docs/` need not be part of the user-facing bundle when its root is a subdirectory. If project rules forbid or contradict this requirement, or the selected location is ambiguous, ask the orchestrator or human to resolve the conflict. Do not apply KOS's chosen subdirectory to another project.
2. Read the bundle index and applicable specifications before planning, implementing or fixing user-facing behavior. Organize concepts by business domain or game aspect, not task ID or implementation component; keep domain navigation and cross-links useful. For a new project establish the smallest navigable bundle needed for its approved requirements. Write UTF-8 Markdown with OKF v0.2 frontmatter and nonempty `type` on each concept (for example `type: Requirement Specification`); only the bundle-root `index.md` may carry `okf_version` frontmatter. Do not label an unapproved draft `stable`, or claim `verified: human:...` without a real verification event.
3. For an approved Brief, create or update the domain concepts describing **what should happen**: full approved normal, alternative, error and significant edge cases, observable results, limits, decisions and testable acceptance criteria. Distinguish explicit approval from proposals, open questions and technical choices; unknown access boundaries or publication destinations require a question, not an invented requirement. Link related requirements and tasks where useful without turning a concept into a task status log or copying the full scenarios into KOS artifacts. KOS keeps a short self-contained snapshot of approved boundaries and significant limits/open questions with the project concept path and verifiable revision. Publish the approved specification before dependent work is unblocked. Planning of an individual Execution or Fix task reads the same normative documents; if that planning reveals a missing or changed requirement, obtain explicit human agreement and update the relevant concepts before implementing against the new norm. Fixes without a Brief use the same rule. Do not silently rewrite a requirement to match existing code or a failing test.
4. A person or agent may prepare a draft through this skill outside KOS; that does not by itself approve a change to required behavior. Record the decision and obtain explicit human agreement before treating new or changed requirements as normative, regardless of author or workflow. Published approved documents are read by subsequent KOS work. If approval or publication is unclear, report the gap; do not present a draft as an approved requirement. Code and tests provide evidence of **actual** behavior; a second document describing current behavior is not required.
5. At a KOS documentation step, inspect the relevant approved user-facing concepts and applicable rules against decisions made during this task. Edit approved requirements or project rules only when agreed changes are needed or a previously agreed rule is missing; get human agreement on a material change to either. Consider whether a significant lasting technical decision needs an ADR explaining context, considered alternatives, choice and consequences. ADRs are optional OKF concepts (`type: Architecture Decision`) in `docs/adr/`, with an index only when entries exist. If the specification bundle root is `docs/`, ADRs are a section of that bundle: link `docs/adr/index.md` from `docs/index.md`, and keep the subdirectory index without version frontmatter. If the specification bundle root is a different `docs/` subdirectory, `docs/adr/` may be a separate bundle whose root index may declare `okf_version: "0.2"`; link to it from the project's documentation navigation without treating the decisions as user-facing requirements. Do not put an ADR into the behavior specification as an approved user-facing scenario, or use an ADR as the only source of a current development rule: link the rule and its rationale where useful. Preserve superseded decisions as history, with links to their replacements; do not silently rewrite their rationale. If neither rules, requirements nor ADRs changed, identify what was inspected and why no edits were needed in `documentation_report`. Record concrete documentation findings with location, effect and verified correction, or explicitly state that there were none. Check OKF frontmatter and applicable project checks, review the diff and report paths, approvals, checks and unresolved conflicts. Publication follows the assigned workflow and the target project's rules.
