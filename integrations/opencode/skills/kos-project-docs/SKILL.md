# Document the target project's behavior

This skill is invoked explicitly by a workflow step, not automatically for every KOS task. Work in the target project's checkout or task worktree provided by the orchestrator. Follow `kos-executor` for delegated step packets, claim-protected KOS artifacts and reporting; this skill concerns the project's own documentation files. A task artifact is not a substitute for the project's maintained documentation.

1. Read the applicable project instructions (such as `AGENTS.md`) and the documentation step's instructions. Find a requirement to maintain documentation **and** its project-specific path. If no project rule requires documentation, report that no project documentation update is required for this step. If documentation is required but its path is missing or ambiguous, do not create a documentation tree or guess a path: report what decision is needed to the orchestrator/user. Resolve the specified path relative to the target project's checkout, following its rules; do not assume KOS's `docs/knowledge/` applies elsewhere.
2. Inspect existing documents and any index or navigation conventions at that path, plus the relevant task result, tests and current user-visible behavior. Update the appropriate existing concept when possible; create a new one only for a distinct user-facing concept. Describe normal, alternative and error scenarios, observable outcomes and limits. Distinguish implemented behavior from planned behavior; do not claim tests, human verification or release that did not occur. For a task with no user-facing change, inspect the affected concepts and report why no behavior update is needed.
3. Use the documentation format required by the project. If it requires [OKF v0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md), write UTF-8 Markdown concepts with YAML frontmatter and a nonempty `type`; `title`, `description` and `tags` are useful when appropriate. Keep `index.md` navigable when the project has one (only the bundle-root index may have `okf_version` frontmatter); do not assign `verified: human:...` without real human review. If OKF is **not** required, follow the project's established format and do not convert existing documentation to OKF. Preserve unrelated content and metadata.
4. Check changed links, frontmatter when OKF applies, agreement with actual behavior, and the project's documentation checks. Review the documentation diff and report edits, verification and unresolved questions to the orchestrator. On re-entry, inspect the current files before editing again rather than adding a duplicate concept or index entry. Publication and step advancement remain the main agent's responsibility.
