# Set up KOS with OpenCode

In installation and update conversations follow the same KOS dialogue rules as task work: use the person's language (or the target project's required language), explain each decision and outcome in plain terms without unnecessary jargon or loanwords, and give enough context in progress and final reports. In ordinary chat ask one question at a time and wait for the answer. A question wizard may contain several questions only if it presents them sequentially. For each decision give a recommendation with a short reason in parentheses; for unknown facts suggest how to establish them instead of guessing. Keep separate required approvals separate, including migration and server restart.

Follow the repository's README "Server Setup", "CLI Installation", "OpenCode Integration", and "Updating an existing installation" sections as appropriate. On a new installation initialize and seed the bind-mounted database using the Docker Compose commands in README, then run the server in the foreground with `mise run kos` on loopback port 3137. For an update, inspect the checkout, persistent database and running process first; fetch from the expected GitHub origin and fast-forward only a clean main. Never discard local commits or changes. Build and install the CLI gem, then run `ruby script/install-opencode` from the KOS checkout. The installer updates only files matching known previous KOS versions; it stops before copying if a destination was modified or is of unknown origin. It also installs the `/kos-init`, `/kos-update`, and `/kos` commands.

Updating files is not consent to migrate the persistent SQLite database or stop/restart the Rails container (or an older `kos.service`). Check pending migrations and their effects first. Before requesting separate explicit migration approval, create and verify an online backup as described in README; ask independently for approval to stop/restart the server. After confirming the schema is compatible (and completing an approved migration if needed), inspect the shared definitions and run the seed in the container as part of installation: it may replace a differing **unused** definition but refuses to replace or remove one used by tasks. Report a seed conflict rather than altering the existing task's workflow. If declined, report which components remain on the old version. Do not automatically restore on failure or claim an update succeeded when some components failed.

Ask the user to quit and restart OpenCode after installation to load new commands and skills. Check `kos` is on PATH, `opencode models openai` lists `openai/gpt-6-luna` and `openai/gpt-6-sol`, and `opencode agent list` shows `kos-standard` and `kos-advanced`. For a **selected target project**, follow [project onboarding](../../project-onboarding.md) to prepare or verify its Git `origin` and conservatively create or extend that project's `AGENTS.md` with KOS task guidance. If no target project was identified during machine setup, report that project onboarding remains; do not write to arbitrary repositories or the global AGENTS.md. In the target repository, load `kos-orchestrator` for an actual KOS task request or use `/kos`. The main agent obtains a conversation ID with `kos session new` when needed; do not ask the user to choose `KOS_SESSION_ID`. If setup fails, report the failed check and recoverable next action without changing unrelated user configuration.
