# Orchestrate KOS steps

Work in the target Git checkout, or pass `--project` with its canonical repository key. Load this skill when the user actually requests KOS work, not merely because KOS is mentioned. `/kos` is an optional shortcut. For a new project without a checkout or `origin`, load `kos-project-onboarding` and follow its complete procedure; a proposed key is not a verified repository. For an existing prepared project, do not load onboarding merely to work on its tasks. Delegated executors only execute assigned steps; they do not independently orchestrate. The KOS server is the source of truth.

For newly created tasks select the installed shared KOS Brief v5, KOS Execution v5 or KOS Fix v5 by its verified workflow ID, as appropriate; do not fall back silently to an older edition if v5 is missing. Existing tasks retain their assigned edition and steps. If an older Brief asks for a dependent Execution of an older edition, keep its approved context and reconcile the choice of edition with the human before creating new work; do not silently switch its dependent tasks to another edition.

Global CLI options precede the resource: `kos --project KEY --session ID task list`, not `kos task list --project KEY`. To compare one saved output with its template without displaying every input artifact in the main context, filter CLI JSON before showing it: `kos --project KEY task step show ID | jq -r '.data.step.templates.test_report'` (replace the key). The full packet still travels from the server to the local filter; this is only output filtering. The brief packet omits templates. When selecting a template from `workflow show ID`, likewise filter the chosen step and output rather than displaying the entire workflow.

For a selected task needing only status, current step, availability and own artifact versions, prefer `kos task show ID --state`; follow its artifact pagination when incomplete. Use `--brief` when dependencies or artifact sources matter. Read the latest `review_report` by key when its findings or evidence matter; a local JSON filter can limit what is displayed in the main context, but inspect the whole report for review decisions. Do not ask the server to interpret its Markdown verdict.

Before relying on an earlier CI or review, compare the current Git base and uncommitted change set to the states recorded in test_report and review_report. A matching commit alone does not cover uncommitted edits. Refer to the reports by lock_version and record new edits and affected reruns instead of repeating the full check list; repeat full CI only when project rules require it or the previous result no longer covers the final change. Independent review of high/medium corrections and changed reviewed behavior is still required.

When selecting among tasks, use `kos task list` first. Read `task show ID --state` for the selected candidate when its status, availability or own artifact versions matter; use `--brief` if dependencies or artifact sources matter. Do not inspect every candidate's large dependency and artifact lists by default. After a successful `advance`, use its returned route without a routine `current` call. Check saved outputs against the templates in the full step packet (the brief packet omits templates); if the executor read the full packet but you did not, retrieve the full packet or assigned workflow definition for the comparison. Inspect evidence and contents, not headings alone. Read only the needed artifacts into the main context and pass no full texts to subagents. A human product decision goes through you: obtain explicit agreement and relay the answer to the executor before any newly required behavior is documented as approved or implemented. An artifact saved with an open product question does not count as that agreement. After a correction or late edit rerun affected checks; repeat full CI only when target-project rules require it or the previous result no longer covers the change. Independent review remains mandatory after high/medium corrections and changes to reviewed behavior.

Speak to the human in their language, or the language explicitly required by the target project's `AGENTS.md`. In questions, progress updates, blockers and final reports, use plain, understandable language without unnecessary jargon or loanwords (except common terms and exact command/file names). Give enough relevant context to understand the issue, why a decision matters and its consequences, but keep each message focused. In ordinary chat ask only one question at a time; wait for its answer before asking the next, even when several decisions remain. If the environment provides a question wizard that actually presents questions one at a time, use it when helpful: it may contain several questions presented sequentially, but never display several questions at once. Do not assume every harness has this feature; if unavailable, use ordinary chat. For a choice, label up to nine options `1.`, `2.`, ... and request a reply with one digit for that question; make option numbers unambiguous and separate from significant question IDs (Q-01, etc.). Recommend a genuine option with a short reason in parentheses, without hiding material tradeoffs. For a free-form question, give a helpful recommendation or proposed next step with a short reason in parentheses where supported by known facts; do not invent a preferred factual answer. Ask plainly without invented choices. Explicit approval of a Brief's requirements or another protected decision must be sought after presenting the relevant summary, not inferred from answers to earlier questions or a mode switch. Pass project language instructions to executors via the checked-out project's rules; their internal step reports should remain understandable to the main agent.

In read-only Plan, discuss a Brief's high-level choices and plan with the human; read existing KOS data if useful, but do not claim, create groups/tasks, write artifacts, or change project files. Before writing, summarize explicitly approved behavior, proposals, questions awaiting answers and technical choices for execution. Clarify the publication route and whether access is local/trusted or external rather than inventing a rule from technical assumptions. Seek separate explicit approval of required behavior and the high-level plan. Full approved scenarios live in the project's domain concepts; KOS keeps a short self-contained snapshot with source path and verifiable revision, approved boundaries and open questions. In a new-project conversation, agree separately on repository setup before doing that setup in Build; creating the initial Brief task is allowed then, but does not count as agreement on its requirements. Number significant questions consecutively across the Brief conversation and retain their answers or unresolved status and the rationale for decisions. After agreement, carry the decisions into Build for all writes. If Build is unavailable, ask the human to switch to Build and continue with the agreed context. Do not interpret the switch itself as consent to previously undecided Brief choices.

Identify the working conversation before any claim. If its history already contains a KOS session ID, reuse it; never generate a second ID on continuation. Otherwise, run `kos session new` once for this independent conversation, retain `data.session_id` in conversation context, and pass it as `--session SESSION` on each session-scoped CLI call (or set `KOS_SESSION_ID` for that conversation). Do not create a new ID per command or share one among independently running agents. Existing external clients may still supply their own IDs.

For a **new** conversation asked to resume an existing task, first identify the intended project and task using `kos task list` and `kos task show ID --brief`. Brief view omits the previous session ID; if the old lease is still active and takeover is necessary, read `kos task show ID` for its session metadata only after identifying the task. If several tasks match, ask which one. If the old lease is still active, ask for explicit confirmation that the old agent has stopped **before** using that old session ID for `current --fingerprint`; then verify project, task ID, current step, expiry and existing worktree before continuing under that ID. Do not silently take over a live claim. Without confirmation, wait for expiry or have the old conversation release its claim. If the lease has expired, generate a new ID for this conversation, claim the available task with `--fingerprint`, and verify the new fingerprint, saved step, artifacts and worktree. If another owner has claimed it or it is done, do not write under an old fingerprint. KOS cannot establish that the old process has stopped touching files.

1. With the retained ID, run `kos --session SESSION task current --fingerprint` first to recover your existing claim. Verify its project, task and step against the conversation; `current` does not renew the lease. If `data.task` is null, check the intended task's state before `kos --session SESSION task claim ID --fingerprint` or `claim-next --fingerprint` in Build. If there is no ready task, check whether the requested task is blocked, owned by another session, done, or not yet created. If nothing actionable remains, explain the state and ask for the specific human decision or action needed to select further work; do not claim the requested task is complete. Inspect `data.task.id`, `claim_fingerprint`, `current_step`, and `step.executor`/`model_tier`. `--fingerprint` requests the compact route but replaces the full claim in CLI stdout with a SHA-256 fingerprint. Never run unfiltered claim/current output in an agent tool, read a claim from a file, or copy a full claim into a prompt or tool arguments.
2. Read `kos task show ID --state` first for status and own artifact versions; use `--brief` when dependencies or sources matter, `kos task artifact get ID KEY` for a needed result, or full `task show` only when its complete context is needed. For workflow selection use `kos workflow list --brief` before `workflow show ID`. Read applicable project instructions and approved OKF v0.2 domain specifications in `docs/` or the project's chosen subdirectory, including documents prepared outside KOS. Code and tests show actual behavior; approved concepts define required behavior. If the task calls for development or for editing and publishing a Brief specification in the project repository, load `kos-task-worktree` and prepare or recover its dedicated Git branch and worktree **before** changing project files or delegating. Do not infer development from an arbitrary task `kind`. Tasks without repository edits can run in the target checkout. For `executor: main`, run `kos task step show ID --brief` to orient yourself; read the full packet when inputs or templates are needed for the work. If the step explicitly calls for `kos-project-docs` (including a Brief specification or changed requirement during task planning), load it; do not invoke it automatically. For `executor: subagent`, invoke only `kos-standard` for `model_tier: standard` or `kos-advanced` for `model_tier: advanced`. Pass ID, canonical project key, absolute task worktree path (or target checkout for tasks without repository edits), step position, the stable `KOS_SESSION_ID`, and `claim_fingerprint` only; no secret, instructions, artifact contents, or full step packet. For correction, also pass only the finding IDs and ask the executor to fetch the latest `review_report` itself. The subagent fetches the packet. Do not allow independent agents to work concurrently on the same claim.
3. Inspect the executor's result and actual check evidence according to the step instruction and target-project rules; KOS does not grade output. For each expected output inspect the saved artifact against its packet template when present, without treating headings alone as evidence. Continue through recoverable errors, remaining steps, checks, corrections and publication without routine approval pauses. Ask a human only for a genuine unresolved product decision or an action the agent cannot safely perform. On a Brief agreement step, you (the main agent) discuss and obtain explicit human agreement on high-level choices and plan **before** writing KOS artifacts, creating dependent tasks/groups or editing the normative project specification; preliminary new-repository setup is agreed separately. Do not delegate that conversation. If the agreement cannot be recovered on resumption, clarify it again. On a Brief publication step, verify the normative specification at the project-defined destination before completing Brief and unblocking its tasks; ambiguous publication requires inspecting the destination. On a review step, use a separate reviewer invocation from the implementation executor. Require evidence-based high/medium/low findings, arrange corrections by an implementation executor for every high or medium finding, rerun affected checks, update test_report with the new evidence and repeat independent review on that same step. Record any deferred low finding and its rationale. Do not advance with unresolved high/medium findings. Renew a still-active claim with `kos --session SESSION --claim-fingerprint HASH task renew ID` before long work when needed (lease is one hour), especially before delegation; after a long delegation verify ownership again. A blocked subagent invocation may prevent renewal during its run; do not promise uninterrupted ownership. If lease expired or claim changed, stop protected writes, inspect current state and re-claim only if available, then verify saved results and worktree before resuming; never reuse the old fingerprint or let a stale executor write.
4. If another step remains, check its expected results and run `kos --session SESSION --claim-fingerprint HASH task advance ID --expected-step N` with the observed position. On success, use the returned `data.task.current_step`, `step` route and `claim_fingerprint` for the next step; do not repeat `current` just to confirm that result. Read `current --fingerprint` after a long pause or ambiguous result, or when recovering ownership; a successful advance is not proof of ownership for a later protected write. Before delegating publication, inspect the final change including documentation edits against both the task specification and high-level project requirements. Rerun checks affected by changes since the prior review and update test_report with their actual outcomes. If reviewed behavior changed, commission a separate advanced review of the current diff without assigning the reviewer the publication step or permission to publish; record the renewed verdict in review_report under the current claim and expected step, without moving the task step backwards. Resolve high/medium findings before publication. On a delegated publication step, the executor may publish according to the target project's rules; independently confirm the destination and publication report before calling `kos --session SESSION --claim-fingerprint HASH task complete ID --work-summary '...'`. Only complete after the required work is done. If a task worktree exists, retain it until publication is confirmed and it is safe to clean up, regardless of the KOS task status; follow the cleanup and recovery procedure in the already loaded `kos-task-worktree` skill.

Use CLI JSON and exit status together: `0` with `data.task: null` means no work/current claim; `4` is a conflict (including `step_conflict`); `5` is `ambiguous_result`. On a conflict or ambiguous mutation, inspect `current --fingerprint` under the retained ID, `task show ID`, or the affected artifact before deciding whether to retry. A wrong ID returns no current task; a changed owner invalidates the old fingerprint, while a changed step requires checking the expected position before another write. Never blindly replay a mutation. A fingerprint is not authorization and the local server does not protect against untrusted local processes.

For work likely to outlast the lease, agree on a bounded checkpoint in the delegation: ask the executor to stop and return a concise progress report before the expiry shown in the route, even if the step is unfinished. After it returns, verify the same task, step and fingerprint with `current --fingerprint`, renew while the claim is still active, then resume the same step under the retained KOS session ID. Do not run two executors concurrently or let an old invocation keep editing after starting its replacement. A single blocked invocation or command can still outlast the lease; if it does, stop protected writes, check the actual task, artifacts and worktree, and re-claim only if available. After a new claim, pass its new fingerprint to the executor and recheck work done during the gap. No background heartbeat is implied. The latest `review_report` determines the review verdict; older `test_report` statements about a pending review describe the state at their time and do not override a later verdict. Keep checks after corrections and the independent review as separate evidence.

For transient CLI/network errors, investigate and retry only when safe after checking whether a mutation took effect; do not spin indefinitely. On `connection_error` reporting refusal at the default `127.0.0.1:3137`, check that the existing local server is running; if it is stopped, ask the human to run `mise run kos` in their terminal and retry once it responds. Do not initialize the database or read the full installation instructions solely for this case. A timeout, malformed response or custom URL requires checking its actual cause; an ambiguous mutation requires state verification before retry. Escalate a persistent blocker only with the exact human action required, leaving an unfinished task at its actual step. After verified publication and `complete`, report to the human in their language: how the work proceeded (including meaningful checks and review), what changed from the user's perspective, where it was published, what task is next (or that none is known), and recommended next action. If a new session is useful, give a ready-to-use instruction such as opening it in the project and running `/kos` to pick up the next task. For a blocked or unpublished task, report its current step and recovery action, never a completion claim.
