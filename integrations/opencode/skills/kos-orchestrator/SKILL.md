# Orchestrate KOS steps

Work in the target Git checkout, or pass `--project` with its canonical repository key. Load this skill when the user actually requests KOS work, not merely because KOS is mentioned. `/kos` is an optional shortcut. Delegated executors only execute assigned steps; they do not independently orchestrate. The KOS server is the source of truth.

In read-only Plan, discuss and agree on a Brief's high-level choices and plan with the human; read existing KOS data if useful, but do not claim, create groups/tasks, write artifacts, or change project files. After agreement, carry the decisions into Build for all writes. If Build is unavailable, ask the human to switch to Build and continue with the agreed context. Do not interpret the switch itself as consent to previously undecided Brief choices.

Identify the working conversation before any claim. If its history already contains a KOS session ID, reuse it; never generate a second ID on continuation. Otherwise, run `kos session new` once for this independent conversation, retain `data.session_id` in conversation context, and pass it as `--session SESSION` on each session-scoped CLI call (or set `KOS_SESSION_ID` for that conversation). Do not create a new ID per command or share one among independently running agents. Existing external clients may still supply their own IDs.

For a **new** conversation asked to resume an existing task, first identify the intended project and task using `kos task list` and `kos task show ID` (which shows the prior `session_id` and lease metadata without the full claim). If several tasks match, ask which one. If the old lease is still active, ask for explicit confirmation that the old agent has stopped **before** using that old session ID for `current --fingerprint`; then verify project, task ID, current step, expiry and existing worktree before continuing under that ID. Do not silently take over a live claim. Without confirmation, wait for expiry or have the old conversation release its claim. If the lease has expired, generate a new ID for this conversation, claim the available task with `--fingerprint`, and verify the new fingerprint, saved step, artifacts and worktree. If another owner has claimed it or it is done, do not write under an old fingerprint. KOS cannot establish that the old process has stopped touching files.

1. With the retained ID, run `kos --session SESSION task current --fingerprint` first to recover your existing claim. Verify its project, task and step against the conversation; `current` does not renew the lease. If `data.task` is null, check the intended task's state before `kos --session SESSION task claim ID --fingerprint` or `claim-next --fingerprint` in Build. If there is no ready task, stop. Inspect `data.task.id`, `claim_fingerprint`, `current_step`, and `step.executor`/`model_tier`. `--fingerprint` requests the compact route but replaces the full claim in CLI stdout with a SHA-256 fingerprint. Never run unfiltered claim/current output in an agent tool, read a claim from a file, or copy a full claim into a prompt or tool arguments.
2. Read the task and applicable project instructions. If the task calls for development (explicitly in its description or in project rules), prepare or recover its dedicated Git branch and worktree **before** changing project files or delegating. Follow the [task worktree procedure](../../task-worktree.md). Do not infer development from an arbitrary task `kind`. Tasks without development can run in the target checkout. For `executor: main`, run `kos task step show ID` yourself and do the instructed work in the task worktree when applicable. If that documentation step explicitly calls for `kos-project-docs`, load it; do not invoke it automatically. For `executor: subagent`, invoke only `kos-standard` for `model_tier: standard` or `kos-advanced` for `model_tier: advanced`. Pass ID, canonical project key, absolute task worktree path (or target checkout for non-development work), step position, the stable `KOS_SESSION_ID`, and `claim_fingerprint` only; no secret, instructions, artifact contents, or full step packet. The subagent fetches the packet. Do not allow independent agents to work concurrently on the same claim.
3. Inspect the executor's result and any required checks according to the step instruction and project rules; KOS does not grade output. Keep working without unnecessary pauses; ask a human only for a genuine unresolved decision. On a Brief agreement step, you (the main agent) discuss and obtain explicit human agreement on high-level choices and plan **before** writing KOS artifacts or creating tasks/groups; do not delegate that conversation. On a review step, use a separate reviewer invocation from the implementation executor; arrange fixes and repeat review at the same step until findings are resolved. Renew a still-active claim with `kos --session SESSION --claim-fingerprint HASH task renew ID` when needed during long work (lease is 30 minutes). If lease expired or claim changed, stop protected writes, check `kos task current --fingerprint` and re-claim only if available; never reuse the old fingerprint.
4. If another step remains, check its expected results and run `kos --session SESSION --claim-fingerprint HASH task advance ID --expected-step N` with the observed position. Read the new compact route with `kos --session SESSION task current --fingerprint` and repeat. Before delegating publication, inspect the final change including documentation edits and rerun checks affected by changes since the prior review; resolve findings before publication. On a delegated publication step, the executor may publish according to the target project's rules without a separate per-step authorization; independently confirm the destination and publication report before calling `kos --session SESSION --claim-fingerprint HASH task complete ID --work-summary '...'`. Only complete after the required work is done. If a task worktree exists, retain it until publication is confirmed and it is safe to clean up, regardless of the KOS task status; follow the cleanup and recovery procedure in [task worktree](../../task-worktree.md).

Use CLI JSON and exit status together: `0` with `data.task: null` means no work/current claim; `4` is a conflict (including `step_conflict`); `5` is `ambiguous_result`. On a conflict or ambiguous mutation, inspect `current --fingerprint` under the retained ID, `task show ID`, or the affected artifact before deciding whether to retry. A wrong ID returns no current task; a changed owner invalidates the old fingerprint, while a changed step requires checking the expected position before another write. Never blindly replay a mutation. A fingerprint is not authorization and the local server does not protect against untrusted local processes.
