# Orchestrate KOS steps

Work in the target Git checkout, or set `KOS_PROJECT` to its canonical repository key. Use one stable `KOS_SESSION_ID` per independently working OpenCode session; do not invent a new identity on each CLI call or share one across concurrent sessions. The KOS server is the source of truth.

1. Run `kos task current --fingerprint` first to recover your existing claim. If `data.task` is null, run `kos task claim-next --fingerprint` (or `kos task claim ID --fingerprint`). If there is no ready task, stop. Inspect `data.task.id`, `claim_fingerprint`, `current_step`, and `step.executor`/`model_tier`. `--fingerprint` requests the compact route but replaces the full claim in CLI stdout with a SHA-256 fingerprint. Never run unfiltered claim/current output in an agent tool, read a claim from a file, or copy a full claim into a prompt or tool arguments.
2. Read the task and applicable project instructions. If the task calls for development (explicitly in its description or in project rules), prepare or recover its dedicated Git branch and worktree **before** changing project files or delegating. Follow the [task worktree procedure](../../task-worktree.md). Do not infer development from an arbitrary task `kind`. Tasks without development can run in the target checkout. For `executor: main`, run `kos task step show ID` yourself and do the instructed work in the task worktree when applicable. For `executor: subagent`, invoke only `kos-standard` for `model_tier: standard` or `kos-advanced` for `model_tier: advanced`. Pass ID, canonical project key, absolute task worktree path (or target checkout for non-development work), step position, the stable `KOS_SESSION_ID`, and `claim_fingerprint` only; no secret, instructions, artifact contents, or full step packet. The subagent fetches the packet. Do not allow independent agents to work concurrently on the same claim.
3. Inspect the executor's result and any required checks according to the step instruction and project rules; KOS does not grade output. Renew a still-active claim with `kos --session SESSION --claim-fingerprint HASH task renew ID` when needed during long work (lease is 30 minutes). If lease expired or claim changed, stop protected writes, check `kos task current --fingerprint` and re-claim only if available; never reuse the old fingerprint.
4. If another step remains, run `kos --session SESSION --claim-fingerprint HASH task advance ID --expected-step N` with the observed position. Read the new compact route with `kos task current --fingerprint` and repeat. On the final step, run `kos --session SESSION --claim-fingerprint HASH task complete ID --work-summary '...'` only after the required work is done. The main agent handles publication using the target project's rules. If a task worktree exists, retain it until publication is confirmed and it is safe to clean up, regardless of the KOS task status; follow the cleanup and recovery procedure in [task worktree](../../task-worktree.md).

Use CLI JSON and exit status together: `0` with `data.task: null` means no work/current claim; `4` is a conflict (including `step_conflict`); `5` is `ambiguous_result`. On a conflict or ambiguous mutation, inspect `current --fingerprint`, `task show ID`, or the affected artifact before deciding whether to retry. Never blindly replay a mutation. Keep `KOS_SESSION_ID` unique and stable; a fingerprint is not authorization and the local server does not protect against untrusted local processes.
