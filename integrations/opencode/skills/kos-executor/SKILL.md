# Execute a KOS step

In test_report identify the Git base and uncommitted change set covered by checks, including untracked files; distinguish changes to file contents from an unchanged list of filenames (for example by recording a diff fingerprint and identifying untracked contents). Record changes and reruns after corrections. In review_report and publication_report cite the earlier report lock_version, checked state and changes since then instead of repeating its check list. Compare the current state before relying on earlier evidence: a matching commit alone does not cover uncommitted edits. Rerun affected checks after changes; repeat full CI only when project rules require it or previous evidence no longer covers the resulting change. Independently re-review high/medium corrections and changes to reviewed behavior.

If review finds a defect in untrusted input, consider other applicable forms of the same flaw (type, encoding, empty value, control characters) and whether a valid request still succeeds afterward; select meaningful checks without generating an exhaustive matrix. Before overwriting test_report or review_report, read its current text and preserve a short, self-contained account of earlier evidence, findings and outcomes in the replacement. Identify the Git base and uncommitted file contents before and after edits, changed files, affected reruns and results, the reason to repeat full CI or reuse earlier evidence, open findings and the latest independent verdict. `lock_version` identifies a current artifact edition; it does not provide the overwritten text or a history. Do not present a reference to an earlier version as sufficient evidence by itself.

For product questions, relay a focused question to the orchestrator; it obtains explicit human agreement and sends the decision back. You may save a technical plan with an open question, owner and resolution point, but its existence does not settle the question: do not update approved requirements or implement behavior dependent on the answer until the orchestrator returns the human decision. Then update the relevant concept before implementation. After saving each output, compare its actual contents and evidence to the full packet template when present; `step show --brief` omits templates. Report only a concise result, not the full artifact. After corrections rerun affected checks, including full CI if required by the project or if the prior result no longer covers the diff; a separate reviewer can inspect existing evidence without repeating an unchanged CI run.

For a Brief, do not copy full approved scenarios into each KOS output: use the approved project concept as their source, keep the short self-contained `specification` snapshot needed for recovery, and refer to stable criterion IDs, source paths and versions from plans and publication reports. On a documentation-only change run applicable document checks and all checks explicitly required by the target project's rules. If a commit hook cannot run because its runner is absent, do not count its skipped commands as passed; inspect the hook definition and run applicable required commands directly. If a mandatory check remains unavailable, stop publication, identify the blocker in the task report and tell the orchestrator unless project rules provide another way to satisfy it.

Work in the absolute task worktree path given by the orchestrator for development tasks (including all file edits, commands and checks), or in the target checkout for other tasks. Pass `--project REPOSITORY` before `task` on every CLI call if Git discovery is unavailable. Verify that the checkout's canonical `origin` identifies the delegated project (or matches the explicitly selected project when discovery is unsupported); if the path is missing, points to another project, or is not the task worktree, stop and ask the orchestrator rather than creating a second worktree. The orchestrator gives you task ID, expected step, its session ID and a claim fingerprint (not the claim token). Do not claim, advance, release, complete or remove the worktree on the orchestrator's behalf. Publish only when the current step explicitly instructs you to publish and the target project's rules permit it; that assigned publication step is the task's authorization, so do not request redundant per-step permission.

1. Independently run `kos task step show ID`. Read `data.step.instructions`, `inputs` (including `missing: true`, source task, key and `lock_version`), `outputs` and `templates` for those outputs. Confirm the packet's current position matches the delegated step; otherwise stop and tell the orchestrator. An absent input is not an empty document; report the gap if the instruction needs it. The server does not require outputs to advance, so check the instruction yourself.
Read the full packet for a delegated step when its input texts and templates are needed. For subsequent orientation on the same step, `kos task step show ID --brief` gives instructions and input versions without repeating their contents; retrieve a specific result with `kos task artifact get ID KEY` when necessary. For a correction delegation, read the latest `kos task artifact get ID review_report` and address the named findings; the orchestrator does not pass report contents. If a checkpoint was requested, return progress and remaining work before the lease expires rather than continuing an open-ended call. Do not start another executor; if ownership has changed, stop protected writes and report what happened.
2. Perform the step in the target project, observing its architecture, style, security and development rules as well as applicable high-level and task-specific specifications. Communicate with the orchestrator in a way it can relay in the human's language or the language required by the project's `AGENTS.md`: give enough context, use plain language without unnecessary jargon or loanwords, including in progress and final reports. For planning steps keep significant question IDs consecutive within the task and retain their decisions or unresolved status across step reports. Send human decisions to the orchestrator one at a time, with context and a recommendation with a short reason in parentheses (a suggested way forward, not an invented answer, for factual questions). For genuine choices use `1.`, `2.`, ... with an unambiguous one-digit reply per question. The orchestrator may present several questions in a wizard only if it displays them sequentially; in ordinary chat it asks and awaits the answer to each question separately. On implementation steps add appropriate tests, run relevant checks and report actual results; on review steps inspect the complete diff and check evidence independently, label findings high/medium/low with impact and location, and send high/medium findings to the orchestrator for correction and renewed review. Do not fix findings yourself when assigned as the independent reviewer. Continue through recoverable errors without unnecessary pauses; ask the orchestrator only when a real blocker or human decision prevents progress. When a planning or documentation step explicitly calls for `kos-project-docs`, load it and follow its OKF v0.2 requirements and project-selected path within `docs/`; do not invoke it automatically for unrelated steps. For a publication step, inspect the complete diff, commit history, tests, review and project rules before publishing, verify the result at the project-defined destination, and keep the worktree on failure or ambiguity. The orchestrator verifies the result and completes the KOS task. For a long step, return at an agreed checkpoint before the lease expires so the orchestrator can verify and renew; a read does not renew it. After a long step or loss of lease, report saved results and stop protected writes until the orchestrator verifies ownership and, if available, reclaims.
3. For each output, use its packet template when present as a guide, replace prompts with actual evidence and omit inapplicable sections with an explanation when necessary. Never save unfilled placeholders or assert checks or approval that did not happen. For a custom workflow without a template, follow its instructions. Save UTF-8 Markdown using `kos --session SESSION --claim-fingerprint HASH task artifact put ID KEY --file PATH --expected-step N --brief`. The CLI fetches the current claim internally and checks the task ID, step and fingerprint before writing; do not fetch or print the full claim yourself. For a new artifact omit `--version` (create only if absent); for an existing artifact, first read its current `lock_version` and pass `--version N`. `--file -` accepts stdin. If storage returns `artifact_version_conflict`, `claim_mismatch`, `step_conflict`, or `lease_expired`, stop and report to the orchestrator; do not overwrite blindly.
4. Report results and checks briefly to the orchestrator without copying the whole packet. On exit code `5` (`ambiguous_result`), inspect `kos task artifact get ID KEY` before considering a retry; the write may have succeeded. Do not assert completion solely because a document was saved.
