# Execute a KOS step

Work in the absolute task worktree path given by the orchestrator for development tasks (including all file edits, commands and checks), or in the target checkout for other tasks. Pass `--project REPOSITORY` before `task` on every CLI call if Git discovery is unavailable. Verify that the checkout's canonical `origin` identifies the delegated project (or matches the explicitly selected project when discovery is unsupported); if the path is missing, points to another project, or is not the task worktree, stop and ask the orchestrator rather than creating a second worktree. The orchestrator gives you task ID, expected step, its session ID and a claim fingerprint (not the claim token). Do not claim, advance, release, complete or remove the worktree on the orchestrator's behalf. Publish only when the current step explicitly instructs you to publish and the target project's rules permit it; that assigned publication step is the task's authorization, so do not request redundant per-step permission.

1. Independently run `kos task step show ID`. Read `data.step.instructions`, `inputs` (including `missing: true`, source task, key and `lock_version`) and `outputs`. Confirm the packet's current position matches the delegated step; otherwise stop and tell the orchestrator. An absent input is not an empty document; report the gap if the instruction needs it. The server does not require outputs to advance, so check the instruction yourself.
2. Perform the step in the target project, observing its architecture, style, security and development rules as well as applicable high-level and task-specific specifications. Communicate with the orchestrator in a way it can relay in the human's language or the language required by the project's `AGENTS.md`. For planning steps keep significant question IDs consecutive within the task and retain their decisions or unresolved status across step reports; present genuine choices as `1.`, `2.`, ... and ask for a one-digit reply through the orchestrator. On implementation steps add appropriate tests, run relevant checks and report actual results; on review steps inspect the complete diff and check evidence independently, label findings high/medium/low with impact and location, and send high/medium findings to the orchestrator for correction and renewed review. Do not fix findings yourself when assigned as the independent reviewer. Continue through recoverable errors without unnecessary pauses; ask the orchestrator only when a real blocker or human decision prevents progress. When the documentation step explicitly calls for `kos-project-docs`, load it and follow its project-specific path and format instructions; do not invoke it automatically for unrelated steps. For a publication step, inspect the complete diff, commit history, tests, review and project rules before publishing, verify the result at the project-defined destination, and keep the worktree on failure or ambiguity. The orchestrator verifies the result and completes the KOS task. For a long step, ask the orchestrator to renew the claim before it expires; a read does not renew it. After a long step or loss of lease, report saved results and stop protected writes until the orchestrator verifies ownership and, if available, reclaims.
3. For each output, save UTF-8 Markdown using `kos --session SESSION --claim-fingerprint HASH task artifact put ID KEY --file PATH --expected-step N`. The CLI fetches the current claim internally and checks the task ID, step and fingerprint before writing; do not fetch or print the full claim yourself. For a new artifact omit `--version` (create only if absent); for an existing artifact, first read its current `lock_version` and pass `--version N`. `--file -` accepts stdin. If storage returns `artifact_version_conflict`, `claim_mismatch`, `step_conflict`, or `lease_expired`, stop and report to the orchestrator; do not overwrite blindly.
4. Report results and checks briefly to the orchestrator without copying the whole packet. On exit code `5` (`ambiguous_result`), inspect `kos task artifact get ID KEY` before considering a retry; the write may have succeeded. Do not assert completion solely because a document was saved.
