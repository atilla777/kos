# KOS development task worktree

This is a client-side procedure for the KOS orchestrator. It does not change task state or grant permission to publish. Apply it when the task description or the target project's instructions explicitly call for development, or when a Brief step requires editing and publishing the project's normative specification; do not infer development from `kind`. Read the target project's rules before selecting a branch, path, base revision or publication route. The task title in KOS is not renamed.

## Prepare or recover

1. Confirm the target checkout and canonical project key from its Git `origin` (or the explicitly selected `KOS_PROJECT` when discovery is unsupported). Do not print credential-bearing remote URLs. Confirm the claimed task ID and project match the intended checkout. Follow the project's rules for each of branch naming, worktree naming and placement wherever they exist. For any unspecified name or placement, use the final repository-name component of the **target project's** canonical key, lowercased and reduced to a nonempty Git-safe ASCII slug (`a-z`, `0-9`, `-`), plus the numeric KOS task ID: branch `<slug>/task-<ID>` and sibling directory `<slug>-task-<ID>` next to the target checkout. For example, `github.com/acme/shop` task 42 gives `shop/task-42` and `../shop-task-42`. Never use the name of the KOS installation as a fixed prefix. If the name cannot be reduced unambiguously, ask for a project-specific name. Confirm a proposed path is outside other checkouts and is not already someone else's work.
2. From the target repository, inspect `git status --porcelain --untracked-files=all`, `git branch --show-current`, and `git worktree list --porcelain` before acting. Check whether the task branch already exists with `git show-ref --verify --quiet refs/heads/BRANCH` and interpret its exit status: 0 means it exists, 1 means it does not, any other result needs investigation; an expected missing branch is not a work failure. If it is checked out in an existing worktree, verify that path's repository, `origin` identity, branch and task association before reusing its absolute path. Do not create another worktree, reset its branch or change its files; dirty changes are work to preserve. If the branch exists but has no verified worktree, or the proposed path is occupied but does not identify this same branch and repository, stop and report both the branch and path for manual reconciliation. Do not adopt a worktree merely because its directory name matches.
3. Only when neither branch nor path exists, verify the project-defined integration/base branch and the chosen base revision; do not guess from an unrelated checkout's current branch. Create with `git worktree add -b BRANCH PATH BASE` using the reviewed values. Do not force, prune, reset, stash, or delete anything to make creation succeed. If creation fails, inspect the branch, path and `git worktree list --porcelain` before retrying; a partial result might already exist. Confirm the new worktree's branch, repository identity and clean initial status. Record its absolute path for recovery and pass that same path with the canonical project key, task ID, step, session ID and claim fingerprint to each executor. All file work and checks, including those by the main agent, run in that worktree. No full claim token is passed.

## Publish and clean up

The main agent reads the target project's review, commit and publication rules and follows them, including its chosen destination and method (for example local integration or a PR). Do not assume `main`, a particular remote or a PR. Inspect status, staged changes, history and the complete diff against the destination; publish only when authorized by the request, applicable project rules, or an assigned workflow publication step. Reuse earlier verified repository/worktree identity and checks while the relevant state is known unchanged; verify status and diff again after edits and before publication. The main agent may delegate that explicit publication step to its designated executor and independently confirms the result at the destination specified by the project (including remote confirmation when a push is required) before completing the task. A KOS `complete`/`done` response, local merge or successful command exit by itself is not proof that publication succeeded. When the outcome is ambiguous, inspect the destination before proceeding. If a hook runner is missing, inspect the project's hook configuration and run the applicable mandatory checks directly; if a mandatory check cannot run, stop publication and report the blocker unless the project's rules permit another way to satisfy it. Never describe a skipped hook as passing.

Only after confirmed publication, verify the task worktree still belongs to the expected repository and branch and `git status --porcelain --untracked-files=all` is empty. Then remove **that** worktree using `git worktree remove PATH` without `--force`; verify it is gone from `git worktree list --porcelain`. Do not remove the branch unless the project's rules explicitly request it. If publication fails, verification is inconclusive, the worktree is dirty, or Git refuses removal, leave it intact and report its absolute path, branch, and the next safe recovery step. A lease expiry, release or task completion does not trigger cleanup. On resumption, verify the claim again and recover the same worktree using the checks above.
