# Make Workflow Execution Generic

## Goal

Make the workflow definition the single source of step execution behavior while
reducing scheduler, CLI, agent, and Git skills to generic reusable mechanisms.

## Product Decisions

- Every workflow step declares `execution_mode` as `main` or `subagent`.
- `main` is valid for built-in and custom workflows without a step-name or task-type restriction.
- Subagent selection uses only the existing `model_tier` value, `standard` or
  `advanced`. OpenCode has no role-specific KOS agents such as plan, brief,
  review, or publish.
- A step's `instruction`, `artifact_template`, and outcomes are the complete
  substantive role contract. Step IDs never imply an executor or Git authority.
- Agents and subagents are trusted to follow workflow instructions. Rails keeps
  only the lifecycle, fencing, artifact, required-check, and brief-graph
  invariants that require deterministic enforcement.
- The CLI generates command-session owner IDs. Models do not generate random
  identifiers.
- The CLI skill includes exact templates for frequent operations. Installed help
  remains the fallback for uncommon operations and compatibility diagnosis, not
  a mandatory call before each known operation.

## Scope

- Add and validate `execution_mode` in workflow definitions and expose it in
  authoritative task context. Preserve existing used workflow revisions with a
  documented effective default while requiring explicit mode in new definitions.
- Mark the built-in briefing step for main-agent execution and all other
  built-in steps according to their intended isolation. Keep independent review
  in a fresh advanced subagent.
- Rewrite scheduling so it follows `execution_mode` and `model_tier` from task
  context without a built-in step dispatch table.
- Let the current command agent execute any `main` step through the same focused
  step/reporting contract used by subagents. Reread authoritative context after
  every step and preserve pause, recovery, and ID-only subagent dispatch.
- Replace role-specific OpenCode agents with one standard-tier and one
  advanced-tier KOS step agent. Remove duplicate role instructions from agent
  profiles; built-in and custom steps receive their role from workflow context.
- Remove step-name authority and workflow-specific review/publication policy
  from `kos-git`. Retain repository discovery, verified task worktree derivation,
  preservation of unrelated state, and concise reusable Git safety guidance.
- Add local `kos session-id`, returning a fresh canonical command-session owner
  generated by a cryptographically secure random source. Use it once per
  scheduler invocation.
- Add common command templates to `kos-cli` for project lookup, request creation,
  resumable selection, claim, resume, context, artifact retrieval, reporting,
  and brief child observation/materialization. Keep values as separate arguments
  and structured content on standard input.
- Remove the redundant `kos-brief` scheduler wrapper or give it only behavior
  that is genuinely specific to executing main-agent steps; do not duplicate the
  shared lifecycle.
- Define terminal handling for cancelled tasks.
- Ensure custom workflow steps, including IDs that collide with former built-in
  names, use only their authoritative execution mode, tier, and instruction.
- Prevent reserved built-in task types from being repointed through the public
  administrative update path to workflow definitions that bypass their
  deterministic server invariants. Catalog installation remains the owner of
  built-in revisions.
- Update product, architecture, installation, testing, and CLI documentation to
  describe the generic execution contract.

## Out Of Scope

- Adding more model tiers or role-specific executor names.
- Treating OpenCode profiles or owner IDs as an authorization boundary.
- Moving Git state into Rails or adding a server-side agent runtime.
- A deterministic Git publication helper or automatic interpretation of
  workflow instructions.
- Changing built-in workflow transitions, required-check gates, or brief graph
  transaction semantics except where needed to express execution mode.
- A new universal workflow capability or permission language.

## Acceptance Criteria

- Task context supplies the authoritative `execution_mode` and `model_tier` for
  the current step.
- The scheduler contains no list mapping step IDs to role-specific agents and
  dispatches subagents with only the positive task ID.
- OpenCode installs exactly two generic KOS step profiles, one standard and one
  advanced, with no built-in role names or duplicated workflow instructions.
- A `main` step in any valid custom workflow executes in the current command
  agent and reports through the same fenced protocol as a subagent step.
- Built-in brief work executes in the `/kos-brief` main agent; its review remains
  an independent advanced subagent and publication remains a standard subagent.
- Custom steps named `diagnose`, `plan`, `implement`, `document`, `brief`,
  `review`, or `publish` receive no implicit role, commit, push, graph, or model
  behavior from those names.
- `kos-git` contains no step dispatch table or built-in review/publication state
  machine.
- `kos session-id` generates `kos-session-` followed by 32 lowercase hexadecimal
  digits without an API token, and scheduler skills no longer ask a model to
  generate randomness.
- Frequent scheduler and step CLI invocations can be formed directly from
  `kos-cli`; help remains documented and usable as fallback.
- Completed and cancelled tasks are both handled as terminal scheduler state.
- Public task-type administration cannot replace a reserved built-in type's
  workflow; custom task types and workflows remain supported.
- Behavioral tests cover both execution modes, both model tiers, custom steps
  colliding with every former built-in ID, owner generation, terminal
  cancellation, main-agent brief execution, and installed asset cleanup.
- Obsolete role-specific profiles and the redundant brief wrapper are absent
  from clean installation output.
- `bin/check` passes.
